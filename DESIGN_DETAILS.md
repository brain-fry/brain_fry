# Design details

Decisions and rationale behind DESIGN.md (Renaud's spec and the core). One section per area: read the section of the area that you work on before you change it. Settled items are stated as facts. Items that still need a decision or a test are in "Still open". Facts about Claude Code were checked against the docs on 2026-11-09.

## Naming and files

- "Brain Fry" in prose, `brain_fry` in code, folders and the package name. `bf` is the command.
- Global, in `~/.brain_fry/` (`BRAIN_FRY_HOME` moves it): `projects.json` (projects and views), `inbox_prompt.md`, the hook script, `extensions/ublock-lite/`, `browser/session_cookies.json` and `browser/firefox_import.json` (see Browser).
- Per project, in `<project>/.brain_fry/`: one task file per session, `<session-id>.md`; `events/`, the spool (one file per hook event, written by the hook, deleted by Brain Fry once applied); `events.jsonl`, the log of applied events (written by Brain Fry only). `consume.lock`: the reader holds it (flock) while it applies the spool, so that `bf list` or `bf consume`, run by hand while the app runs, cannot apply an event twice.
- Why a spool and not one file that the hook appends to: jq may write a long line in several `write` calls, so two hooks that end at the same moment could interleave their lines. And consuming an append-only file needs a saved offset or a rotation, both racy while hooks append. A temp file plus a rename avoids both.
- Task files are not committed. Add `.brain_fry/` to `~/.gitignore_global`. A project that wants them committed negates the rule in its own `.gitignore`.
- `bf init` in a project creates `.brain_fry/` and registers the project in `projects.json`, so the hook condition (folder exists) and the project list never disagree.
- `bf install`, once per machine: adds the hook entries to `~/.claude/settings.json` next to the existing ones (8 events already have hooks there: carbon, statusbar). Safe to run twice, keeps a backup. Adds `.brain_fry/` to `~/.gitignore_global`. Writes a first `inbox_prompt.md`, and installs uBlock Origin Lite (see Browser). Planned with the reply trailer: `trailer_prompt.md`.

## Task file

YAML frontmatter, then the rolling digest, then one section per thread (TT).

- Frontmatter: `session_ids` (a fork gets its own file, see Split), `title`, `short_title` (2 or 3 words, the heading of the card, see Status, inbox, board), `cwd` (where the session started: `--resume` must run there), `transcript_path`, `project`, `prio` (working, planning, later, more_later, never), `status` (working, blocked, waiting, done), `live`, `inbox`, `unread`, `parent` (the task that this one was forked from), `resume_note` (planned, see Resume note), `created`, `updated`, `opened` (last selected in Dev mode, see Project dropdown), `open_files`, `terminal_tabs`, `browser_tabs` (URLs, see Browser).
- Thread section: timestamp, kind (review, answer, rule, FYI, blocked), digest, the question verbatim if there is one.
- Layout: `# Digest`, then `# Threads` with one `## n | timestamp | kind` section per thread, with the parts `**Digest**`, `**Question**`, `**Prompt**`, `**Reply**`, and, once the reply trailer is built, `**Sonnet kind**` when Sonnet disagrees with it. All free text is written as blockquote lines (`> ...`), so no content can be mistaken for structure, whatever headings, fences or `---` lines it holds. The parser reads only the lines without `>` as structure.
- A thread is born at UserPromptSubmit (kind `working`, with the prompt). Stop adds `last_assistant_message` as the reply and sets the kind `pending` (planned: the kind of its trailer, when it has one); the digest then sets the final kind. A new prompt before any Stop (Esc) marks the previous thread `interrupted`. A Stop without a prompt before it (a background task that finishes, or hooks installed mid-session) makes a thread without a prompt.
- The task file keeps the prompt and the full reply of every thread: the digest needs them, and the transcript may be gone after 30 days.
- Until the first digest, a task shows the first line of its first prompt as its title.
- The task file is the record. Claude Code transcripts are deleted after 30 days by default, and their JSONL format is documented as internal. A task must hold everything that Brain Fry needs; the transcript is read as little as possible.
- Per-task workspace: open file tabs and browser tabs (3a) and terminal tabs (3b) belong to the task and are restored when the task is selected. The explorer root (2a) is the task's project.

## Hooks

Source: https://code.claude.com/docs/en/hooks.md

- Stop fires every time Claude finishes a turn and waits for input. It does not fire on a user interrupt (Esc). SessionEnd fires when the CLI exits. The inbox trigger is Stop, not SessionEnd.
- Notification fires with `notification_type` `permission_prompt`, `idle_prompt`, `elicitation_dialog` (and others) when Claude is stuck waiting, after about 6 seconds without typing. That is the blocked case.
- Every payload has `session_id`, `transcript_path`, `cwd`, `hook_event_name`. Stop adds `last_assistant_message` (use it: the transcript may not yet contain the final message). Notification adds `message` and `notification_type`. Session id = task id. The project comes from cwd, see the walk-up below.
- Hooks run synchronously, Claude waits for them. Default timeout is 600 s for command hooks.
- Registered once in `~/.claude/settings.json`, so they run in every project. Events used: UserPromptSubmit, Stop, Notification, SessionEnd. SessionStart is planned, to print the trailer instruction (see Reply trailer).
- The hook is bash plus jq, not `uv run`, because it runs at every turn end. It exits at once when `BRAIN_FRY_INTERNAL` is set. Otherwise it walks up from `$cwd` to the nearest folder that has `.brain_fry/`, and exits if there is none. The walk stops below `$HOME`, because `~/.brain_fry/` is the global folder, not a project. It writes the payload, plus `bf_ts` (epoch seconds, from jq's `now`) and `bf_project`, as one file in that folder's `.brain_fry/events/`. It prints nothing, except my editor selection on UserPromptSubmit (see Selection as context): on UserPromptSubmit and SessionStart, stdout is injected into Claude's context.
- Walking up, and not only checking `$cwd`, keeps the sessions that start in a subfolder or in a worktree under `.claude/worktrees/`. For nested projects, the nearest folder wins.
- Hook processes inherit the environment of the `claude` process (documented). That is what makes the `BRAIN_FRY_INTERNAL` guard work.
- Seen on 2026-11-09 (Claude Code 2.1.318): the Stop payload also has `prompt_id`, `background_tasks`, `permission_mode`, `effort`, `session_crons`, `stop_hook_active`. At the end of a `-p` run, SessionEnd has `reason: other`. Tested end to end with `claude -p --settings` that adds the hook: an event from a subfolder lands in the project's spool.
- `claude --resume <id>` keeps the session id and appends to the same transcript. `--fork-session` gives a new id with the full history. Resuming one id in two terminals interleaves both into one transcript.

Event --> status:

| event | status | color |
|---|---|---|
| UserPromptSubmit | working | orange |
| Notification permission_prompt, elicitation_dialog | blocked | red |
| the dialog closes (no hook: Claude Code's process file, see below) | working, or waiting after a refusal. `inbox` off | orange |
| Stop | waiting (needs me) | green |
| SessionEnd | unchanged, but working or blocked --> waiting (nothing runs any more). `live` off | unchanged |
| archive (my action) | done | gray |
| Stop of my `close` prompt, reply with `closed :-)` | done (archived), `inbox` off | gray |

- A task started from Brain Fry is born at once: `bf` runs `claude --session-id <uuid>`, so it knows the id before the first hook. Prio working, status waiting, `inbox` off. A session started elsewhere is born at its first UserPromptSubmit, Stop or Notification; SessionEnd alone creates no task. When its project was registered in the middle of the session, its earlier turns are imported from its transcript as `imported` threads, as when I drag a session onto the board (Renaud, 2026-11-10). The event's own turn is found by `prompt_id`, which is the `promptId` of its prompt in the transcript (checked on 2026-11-10), else by the prompt's text. A first Stop whose `prompt_id` is not the last prompt's (a background task) gets a thread of its own. Sessions with no `.brain_fry/` in `$cwd` or a parent are ignored. Quick questions and scripted `-p` runs inside a project do create tasks; archive them with one key.
- Stale orange: Stop does not fire on interrupt. If a task is working and its transcript has not changed for a few minutes, show it as stale.
- Red clears when the dialog closes: I granted or refused the permission, or answered the question. No hook fires for that (PreToolUse and PostToolUse would fire on every tool call in every project). Claude Code's process file (`~/.claude/sessions/<pid>.json`, see Other sessions) has `status` `waiting` while a dialog waits for me, with `waitingFor` (seen in the binary of 2.1.322: `input needed`, `dialog open`, a worker or sandbox request, or the dialog's own label), and `statusUpdatedAt` (ms). The scan every 3 s ends the block when a blocked task's process is `busy` (working) or `idle` (a refusal ended the turn: waiting), with a `statusUpdatedAt` after the Notification. That check rejects a snapshot of the files from before the block: the dialog opens about 6 s before the Notification fires. The task leaves the inbox, as after an answer, and the front end advances (see Auto-advance).
- Found on 2026-11-10 (Renaud: "I clicked on the right permission but the task did not disappear"): before this, red cleared only at Stop, so a granted task stayed red in the inbox for the rest of the turn. In that case the dialog was an AskUserQuestion, which also fires `permission_prompt`.
- Without Claude Code's process files (the folder is missing, or untrusted), red clears at Stop, as before.
- How to check an internal format of Claude Code: the binary (`readlink -f "$(which claude)"`, 320 MB) holds its JS source. A Python `mmap` scan for a key (here `statusUpdatedAt`, then `status:"waiting"`) prints the code around it in seconds. `grep -E` with a context pattern did not finish in 120 s, and ugrep refused it (complexity limit).
- Sessions started outside Brain Fry (plain `claude` in a terminal) fire hooks and appear on the board, but have no terminal in Brain Fry. They are read-only until SessionEnd, then resumable. Brain Fry also reads Claude Code's list of running processes, so it knows where they run, and when they end even without a hook (see Other sessions).

## Digest (Sonnet via claude -p)

- Input, rolling: the task's current digest plus the last thread (the user prompt and `last_assistant_message`, tool calls reduced to tool names and file paths, tool outputs dropped). Bounded cost; has goal, question and answer. Weakness: summary errors compound over many turns. Accepted.
- Output, fixed structure through `--json-schema`: title, short title (2 or 3 words), digest of three to five lines, kind (review, answer, rule, FYI, blocked), question verbatim or null. The kind field is what makes the inbox an owner inbox and not a notification list. Planned: when the reply has a trailer, the trailer's kind wins (see Reply trailer).
- One Stop = one turn = one thread. Normally one digest call per turn. The backlog at startup is batched: one call per task covers all of its turns that were not digested yet, and still returns one thread section per turn.
- Title: the first digest sets it, later digests do not change it (a card title that changes every turn is hard to follow). A key renames a task.
- Short title: set once, as the title. A rename sets both, so that my name shows on the card, whatever its length. When Sonnet returns none, the first three words of the title stand in, so that a task never loops on calls for it. The schema describes the field too, so an `inbox_prompt.md` from before the field still gets one.
- Tasks from before the short title (added 2026-11-10): the sweep queues a call for each task that has a digest and turns but no short title. The call sends no turns, and only the short title is applied: title, digest and threads stay. Tried on 4 tasks: "Cmd+N project picker ranked by recent use" --> "Project picker". The digest queue has two priorities, so that these calls (about 25 at the first start) never delay the digest of a turn. A fork without a turn of its own is skipped: a short title made from its parent's digest would name the parent's topic.

```
BRAIN_FRY_INTERNAL=1 claude -p --model sonnet \
  --output-format json --json-schema "$SCHEMA" \
  --no-session-persistence \
  --settings '{"disableAllHooks": true}' \
  "$PROMPT"
```

- Recursion guard: the digest call is itself a Claude Code session and would fire the Stop hook. Primary guard is the `BRAIN_FRY_INTERNAL` variable. `disableAllHooks` is a second layer: the docs say that it overrides project settings and imply that it overrides user settings.
- `--bare` would skip hooks and CLAUDE.md, but in bare mode Claude Code does not read the OAuth login and needs an API key. Not usable with the subscription.
- Without `--bare`, every digest call loads `~/.claude/CLAUDE.md`. Accepted. Running the call with cwd `~/.brain_fry/` avoids at least the project's CLAUDE.md.
- `--no-session-persistence`: no transcript for digest calls. `-p` sessions are hidden from the picker and from `--continue` anyway.
- `structured_output` is missing from the JSON when the run failed. Check before reading.
- Red items get no Sonnet call. The inbox shows "blocked: <notification message>" plus the existing digest.
- Placeholder: the Stop event carries `last_assistant_message`. Show it in the inbox at once and replace it when the digest arrives. The inbox keeps working when Sonnet fails.
- The consumer runs only while Brain Fry runs, in a background thread. On start it digests the backlog. No daemon.
- The prompt goes on stdin (no limit on argument length). Each turn sends the prompt (cut to 4,000 characters), the tools used (from the transcript, best effort: name plus file path or the first line of the command) and the reply (cut to 8,000 characters).
- The call runs without the task-file lock. Afterwards the task is reloaded and only the threads that were sent are updated, because events may have changed the task in the meantime. A thread that the model skipped becomes FYI, so that it never loops. A failed call leaves the thread pending.
- Measured on 2026-11-09: about 3.4 s per call. Tested on a real session: kind `answer`, the question copied word for word, a 3-line digest.
- `bf digest` and `bf list` run the reader and the digest by hand, for testing without the app.

## App

Brain Fry is one Mac window. Chosen on 2026-11-09 instead of the TUI, see Rejected.

- One Python process. pywebview opens a native window that uses the system WebKit (WKWebView), so no browser is bundled. The front end is plain JS: xterm.js for 4a and 3b, CodeMirror 6 for 3a.
- A local websocket in the same process carries the terminal bytes between xterm.js and the PTYs, and pushes board and inbox updates to the front end. Jupyter's terminal works the same way (terminado + xterm.js).
- The app owns the PTYs. Each live session is a `claude` child process in a PTY, with `TERM=xterm-256color` and `COLORTERM=truecolor`. Each terminal tab (3b) is a shell in a PTY.
- Children get a cleaned environment. When Brain Fry is started from inside Claude Code or VS Code, it inherits about 30 variables that they set for their own children (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_ENTRYPOINT`, `VSCODE_*`, `TERM_PROGRAM`, ...). A `claude` that sees them may believe that it is nested or attached to an IDE. The app removes a precise list of them (`CHILD_ENV_DROP` in `util.py`) and every `VSCODE_*` variable, not every `CLAUDE*` variable, because a user may set `CLAUDE_CODE_*` variables on purpose.
- The front end keeps one xterm.js instance per live session and shows the selected one in 4a. Each instance keeps its own scrollback. The backend keeps the last few MB of each PTY's output, so a reloaded front end can replay it.
- Quitting the app ends all live sessions: a turn in progress is killed, and `--resume` brings the conversation back. Quitting asks for confirmation while a task is working. Planned: closing the window keeps the app running. Built in step 3: closing the window quits (with the same confirmation).
- Spawning a PTY child: the app has threads (Cocoa, asyncio, digest worker), so `pty.fork()` (Python code between fork and exec) is unsafe. `subprocess.Popen` forks and execs in C; a 3-line Python wrapper then takes the PTY as its controlling terminal (TIOCSCTTY, so that Ctrl-C and SIGWINCH reach the child) and execs `claude`. Tested: size, SIGWINCH, Ctrl-C.
- Code: `app/core.py` (state, commands, PTYs, the reader every 0.5 s, the digest worker thread, a sweep every 60 s), `app/server.py` (one port: static files, `/file/<task id>/<path>` for the images and PDFs of 3a, `/ctl` websocket for state and commands, `/pty/<task id>` websocket for terminal bytes), `app/main.py` (window, single instance through a lock on `~/.brain_fry/bf.lock`), `web/` (plain JS; the libraries are vendored in `web/vendor/`, see 2a, 3a, 3b).
- The server listens on 127.0.0.1 only, but a web page that I open in a browser can still reach it: a browser opens a websocket to any address (no same-origin rule for websockets), and DNS rebinding lets a site point its own name at 127.0.0.1. Without a check, such a page could find the port, send `shell.new` and type a command into the shell. So every request must carry `Host: 127.0.0.1:<port>` or `localhost:<port>` (a rebinding page sends its own name), and a request with an `Origin` header must come from the app's own page. Clients that are not browsers (tests, scripts) send no `Origin` and pass; they run as me anyway. Built 2026-11-10, tested in `test_app_backend.py`.
- The backend pushes the whole state (all tasks) after every change, coalesced over 50 ms. Simple, and cheap for dozens of tasks.
- Resume: `claude --resume <id>`. A task that was never prompted has no transcript to resume, so it gets `claude --session-id <id>` again; a fork that was never prompted is forked again.
- `~/.brain_fry/owned.json` lists the tasks whose `claude` runs in the app. After a crash, the app marks them not live at the next start (those processes died with it).
- A session that runs elsewhere (live, but not a process of the app) shows an overlay in 4a that says where it runs (VS Code or a terminal, idle or busy): close it there, then resume it here. A button resumes it anyway.
- The project picker (Cmd+N, + New task; Cmd+P, see Project dropdown) asks the backend for `projects.json` each time it opens, and a change of `projects.json` pushes the state: a `bf init` in a terminal shows at once (bug seen by Renaud on 2026-11-10).
- The picker shows the projects in the order of the dropdown (see Project dropdown): the most recently used first. Each row marks the current project and says how long ago I last opened a task there.
- Picker keys: Enter opens the highlighted project (Cmd+N: the first; Cmd+P: the first that is not the current project; until an arrow key moves the highlight), 1 to 9 open the n-th one. Each row shows its key: Enter on the highlighted row, its digit on the others.
- When a Stop arrives for the selected task, it is marked read at once (I am looking at it). It stays in the inbox.
- `bf --browser` serves the same page without a window; `bf --selftest` lets Claude check the window without a human (page text, terminal text, and snapshots taken by WebKit itself, because `screencapture` needs the Screen Recording permission).
- A selftest that selects tasks would resume real sessions. Run it on a sandbox instead: `BRAIN_FRY_HOME` (projects.json and the logs), `BRAIN_FRY_CLAUDE` (a fake `claude` script) and `CLAUDE_CONFIG_DIR` (fake transcripts) point Brain Fry away from the real files. `--selftest-js` then drives the page: set a select's value and dispatch `change`, or focus an element and dispatch a `keydown` on it (see Keys). Used on 2026-11-10 for the project dropdown and Cmd+P. A button of the header: `select(id)`, then `.click()` on `#task-head [data-act=...]` in a `setTimeout` of about 800 ms, because the header is drawn at the next state push (used for Pin).
- To see the board with real-looking cards, copy some real task files into the sandbox project and rewrite their `project` and `cwd` to the sandbox path (also `transcript_path: ''`, `live: false`). The backend writes to the file under `task.project`, so a copy that keeps the real path would change the real task. Used on 2026-11-10 for the short titles; the copies with a digest but no short title then start their calls to the fake `claude` (they fail, as expected).
- Another agent may edit the same front end while a selftest runs. When its unfinished edit calls a function that does not exist yet (on 2026-11-10, `isCut` from the explorer's cut and paste broke every draw of 2a), define a stub at the top of `--selftest-js` (`if (typeof isCut === 'undefined') window.isCut = () => false;`) instead of waiting or changing its code. A browser tab in a selftest needs a page that loads: a failed load becomes `about:blank`, which is never saved. The app's own files work (`location.origin + '/icon.png'`).
- While the app runs, the selftest needs its own `BRAIN_FRY_HOME` (the single-instance lock), its own projects and a fake `CLAUDE_CONFIG_DIR`. With the real projects it would apply their spools in place of the running app. Keys can be tested with `--selftest-js` by sending `KeyboardEvent`s to the element that has the focus in real use (usually xterm.js's textarea in 4a, not `document`), with `newTask` replaced by a function that records its argument, so that no session starts (done for the project picker on 2026-11-10).
- A selftest is valid only while its window is on screen. When other windows cover it, WebKit reports the page as hidden (`document.visibilityState`) and pauses `requestAnimationFrame`, and everything that waits for a frame stops: PDF.js then stops tracking the scroll position. On 2026-11-10 this made a PDF test fail in about half of the runs; every run with the window visible passed. Put `document.visibilityState` in the selftest's output and ignore the runs where it is `hidden`. `--selftest-js` runs once, about 3 s after the start; write the results into a `<pre>` appended to the page, since the selftest prints the page text.
- Icon: `src/brain_fry/web/icon.png`, cropped around the brain from the original image (1.2 MB, kept outside the repo), 256 px, 64 colors: 23 KB (32 colors show rings in the glow). The Dock and Cmd+Tab show `web/dock_icon.png`, the same brain without the dark background and the glow (transparent; Renaud, 2026-11-10: "an ugly black background"), built from `icon.png` by `frontend/dock_icon.py`: the bright pixels plus the dark outline that touches them, holes filled. The splash and the header keep `icon.png`, whose glow matches their background. The Dock icon and the app menu name ("Brain Fry", not "Python") are set through AppKit, because pywebview's `icon` option works only with GTK and Qt. Splash: the icon on `#040510` (the image's background) until the first state arrives, at least 0.9 s; the window background has the same color, so there is no white flash.
- Claude Code runs unmodified in xterm.js (permission prompts, plan mode, slash commands). Shift+Enter is mapped in xterm.js to ESC CR, the bytes that Claude Code reads as a new line.
- Terminal test (step 0, 2026-11-09; its spike, `spikes/terminal/`, was deleted on 2026-11-10 and is in git history). Passed: a real turn with a tool call and a permission prompt, Shift+Enter and Option+Enter, plan mode / Esc / Ctrl-C, multi-line paste and copy, resize, colors, `/help` and `/model`, Option+arrows. Not tested yet: scrollback and find, replay after a page reload, clicking a URL.
- Keys: Cmd shortcuts belong to Brain Fry, because a terminal never sends Cmd to the program inside it. Option is Meta in xterm.js (`macOptionIsMeta`). The native menu of pywebview takes some keys before the page sees them: Cmd+H, Cmd+Option+H, Cmd+Q, Cmd+Ctrl+F, Cmd+X/C/V/A (checked in pywebview's `cocoa.py` on 2026-11-10). Other Cmd keys reach the page.
- While a terminal (4a, 3b) has the focus, the target of a key is xterm.js's hidden textarea (`.xterm-helper-textarea`). The key handler leaves the keys of text fields to them (a rename, a resume note, the browser's address field), but not this textarea. Until 2026-11-10 it skipped every textarea, so no Brain Fry Cmd key worked while the focus was in 4a (Renaud: Cmd+P and Cmd+N "are not working"). The selftests had missed it: they sent the keys to `document`. Fixed and checked with a selftest that sends the keys to the textarea; Renaud has not tried it in the window yet.
- A session without events for 4 h is closed (SessionEnd --> `live` off), except when its task has the `inbox` flag (a pin alone does not keep it). `--resume` restores it, nothing is lost.
- Selecting a task without a live session runs `claude --resume <id>` at once, in the task's `cwd`.
- Each live session is one `claude` process. Claude Code is a native binary (TypeScript, compiled), 320 MB on disk here. Running instances used 80 to 220 MB each on 2026-11-09. Brain Fry has no Node dependency at runtime.

## 2a, 3a, 3b: files and terminals

- Layout of Dev mode: 1 | 2a | 3a over 3b | 4a. The splitters between them can be dragged. Cmd+1 shows or hides 2a, Cmd+2 the middle column (3a and 3b), Cmd+J the terminal panel (3b). When the window is narrow, the middle column gives way first; 4a keeps at least 360 px. Sizes are remembered by the window (localStorage).
- 2a, explorer: the tree of the selected task's project, loaded folder by folder. It hides `.git`, `.venv`, `node_modules`, `__pycache__`, `.brain_fry` and a few other caches. The open folders are reloaded when an event arrives for the task (the agent may have added files), and with Refresh (the right-click menu, or File > Refresh Explorer in the menu bar).
- 2a has no title bar (Renaud, 2026-11-10): the project is in the header's dropdown. Folder names end with `/`, so that folders stand out. A button at the top right, over the first row and not on a line of its own, collapses every open folder (VS Code's "Collapse Folders in Explorer").
- The menu bar has a File menu (Refresh Explorer), right after the app menu. pywebview appends custom menus after Edit and View, and builds the menu bar again when the window becomes key, so `main.py` wraps pywebview's builder to move File (internal to pywebview 6.2; if it changes, File stays at the end). No key equivalents: a key of the menu bar never reaches the page. A menu action runs in a thread and calls `menuAction(name)` in the page.
- Clicks in 2a work as in VS Code (Renaud uses VS Code all the time): a click opens the file and leaves the keyboard in the tree, so that Enter renames; a double-click (the second click, see Modes) moves the keyboard to the file. Before 2026-11-10 a click moved the keyboard to the file.
- Right-click menu of 2a (`web/explorer.js`), asked by Renaud on 2026-11-10 from his VS Code habits: Open in default app (Open in Finder for a folder), Cut, Copy, Paste, Copy path, Copy relative path, Rename (Enter), Delete (Cmd+Backspace), Refresh. On the empty space under the tree: Paste (into the project folder) and Refresh. Keys, while the tree has the keyboard: Enter or F2 renames the selected entry, Cmd+Backspace deletes it.
- Rename: a field in the row, the name without its extension selected. Enter or a click elsewhere keeps the new name, Esc cancels. 2a is not redrawn while the field is open. A name with `/` is refused (that would be a move), and so is a name that is taken; a change of case only is allowed (one entry on macOS).
- Delete moves the entry to the Trash of macOS (`NSFileManager.trashItemAtURL`), after a confirmation, so Finder can put it back.
- Cut / Copy keep the entry in Brain Fry (not on the clipboard of macOS: Finder cannot paste it), and a cut entry is dimmed. Paste goes into the folder that was right-clicked, or into the folder of the file. A copy never replaces anything: it takes the name that Finder gives ("a copy.py", "a copy 2.py"). A move onto a taken name is refused; a cut is pasted once. Paste works across projects (the source is the task where I chose Cut or Copy).
- Copy path / Copy relative path: the path as the tree shows it (symlinks not followed), relative to the project folder, not to the task's `cwd`. The backend writes it with `pbcopy`, under a UTF-8 locale, or accents come out wrong.
- A symlink is renamed, moved and trashed as a link, never its target (`files.entry` resolves only the folder of the entry).
- Tabs follow: a renamed or moved file keeps its tab, in every task of the project (tasks of one project share its files), with its unsaved edits and the language of its new extension. A deleted file's tab closes, except with unsaved edits: it then stays as "Deleted on disk", and Save writes the file again.
- 3a, file tabs: CodeMirror 6, editable. Editing is required before Brain Fry is usable (Renaud, 2026-11-09). Cmd+S saves. "Diff vs HEAD" shows the changes against git HEAD inside the editor (unified view, `@codemirror/merge`); the file stays editable.
- The agent writes the same files. Brain Fry checks the open files every 2 s (version = mtime and size). A file without my edits follows the disk. A file with my edits shows "Changed on disk", with two buttons: reload (drop my edits) or overwrite with mine. A save refuses to overwrite a file that changed since I opened it, and shows the same choice.
- A save is atomic and keeps the file's mode (a script stays executable) and its line separators (CRLF stays CRLF). Text files over 2 MB are not opened. Paths must stay inside the project.
- Images and PDFs open in viewers, as tabs of 3a (built 2026-11-10, asked by Renaud). The kind comes from the extension (`files.view_kind`). The images are what WebKit decodes: PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, TIFF, HEIC. SVG is text and stays in the editor. The bytes come over HTTP from `/file/<task id>/<path>?v=<version>`, not as text over `/ctl`: `<img>` and PDF.js want a URL, the browser streams the file, and a 20 MB PDF does not block the websocket of state and commands. The route serves only those extensions, inside the project, up to 200 MB, with `nosniff` and `Content-Security-Policy: sandbox`, so that it can never serve a page that runs in the app's origin.
- A viewer has no edits, so it always follows the disk: the 2 s poll sees the new version and reloads it (a new `?v=` URL, never a cached copy). A file that is half written fails to load: the old one stays on screen, and the next version is tried at the next poll. A version that failed is not fetched again. A file that comes back as it was clears "Deleted on disk".
- Image: fits the panel and is never enlarged; a click on it or the 100% button shows it at its size. A checkerboard shows transparency. The bar shows the size in pixels and in bytes. A new version is loaded aside, then swapped in, without a blank between the two.
- PDF: PDF.js's page viewer (`PDFViewer`, `PDFLinkService`, `PDFFindController`): continuous scroll, text selection, links (web links open in the default browser), fit to the width at first. Its tools sit in the bar: page box, zoom (- / + / a list: Width, Page, 50% to 200%; Cmd+scroll and pinch), find (Cmd+F, Enter next, Shift+Enter previous, Esc back to the PDF, a count "1 / 2"). A reload keeps the page, the point on it and the zoom (Renaud: "I want the PDF to refresh when the file is refreshed").
- The bar of 3a is rebuilt only when its HTML changes, and the PDF's tools are one element that moves into it: `render()` runs at every state push, and a rebuild would take the focus out of the find field.
- PDF.js's viewer does not fit itself to a new size (its app does it on a window resize), so a ResizeObserver on the container fits it again (Width, Page). A PDF tab that is hidden (another tab, Cmd+2, Organize mode) may come back with its scroll position reset: the tab keeps the last location that PDF.js reported while it was on screen (`updateviewarea`: page, and the point at the top left in PDF units) and goes back to it when it shows. Reports are ignored while the tab is hidden and until that restore has run, since PDF.js may report page 1 first. A reload uses the same location, so it also works while the tab is hidden. A PDF opened while its tab is hidden (restored with the task) gets a scale for a width of 0 (negative); the fit on showing corrects it.
- Other binary files and text files over 2 MB: a toast with an "Open in default app" button (`fs.open`, macOS `open`). Images and PDFs have the same button in the bar.
- In a code editor, the editor keeps Cmd+D (next occurrence) and Cmd+Up/Down (start / end of the file); the other Brain Fry keys still work.
- 3b, terminal tabs: one shell (`$SHELL -l`) per tab, in a PTY of the app, started in the task's `cwd`. `exit` closes the tab. Hidden tabs keep running.
- A task's open files (`open_files`) and terminal tabs (`terminal_tabs`, their names) are saved in its task file. When the task is selected for the first time after a start, they come back: the files reopen, and fresh shells start (the old ones and their scrollback ended with the app).
- A new task (Cmd+N, + New task, "New task in <project>") starts with the tabs of the previous task (Renaud, 2026-11-10: "the exact same setup"). The previous task is the selected one if it is in the new task's project; else the task of that project that I opened last, archived ones included (a task that I just archived is often the one that I continue). The front end picks it (`newTask`, `from` in the `new` command); the backend copies its `open_files`, `browser_tabs` and `terminal_tabs` into the new task file (`actions.new_task`) and starts one fresh shell per terminal tab, in the project root. The front end then copies the view: the tab on screen and the open folders of 2a (`copyView`). A browser tab on screen is matched by its position among the saved tabs, since each tab has a new key. Not copied: thread tabs (the new task has no threads), unsaved edits (the new tab reads the file from disk), a page's history, and what the old shells hold (their scrollback, their current folder). A task of another project is never a source: its paths belong to that project, and the backend refuses it. The backend copies from the task file, which is current; the front end's copy of a task's lists may be older, because `files.set` and `browser.tabs.set` push no state.
- A fork starts with its parent's tabs in the same way (Renaud, 2026-11-10), its shells in the parent's `cwd`.
- JS libraries: `frontend/vendor.sh` builds `src/brain_fry/web/vendor/` once with Node (npm, esbuild): xterm.js as it is, CodeMirror as one bundle (722 KB) with the languages Python, JS/TS, JSON, Markdown, HTML, CSS, YAML, SQL, shell and TOML, and PDF.js 6.4.299 (4.6 MB, 283 files: the library, its worker, the page viewer component minified by esbuild, character maps and standard fonts for PDFs that do not embed theirs, the wasm decoders of JPEG 2000 and JBIG2, a color profile; not the full viewer app nor the JS engine of PDF forms). PDF.js is loaded at the first PDF, not at the start.
- PDF.js and the system WebKit (macOS 26, checked on 2026-11-10): PDF.js 6 reads the text of a page with `for await` over a `ReadableStream` (also in its worker, to decompress some images), and this WebKit cannot iterate a stream (`ReadableStream.prototype[Symbol.asyncIterator]` is undefined). Pages render without it, but find matched nothing. The legacy build, which is vendored for its other polyfills, has the same code. `web/pdf_polyfill.mjs` adds the iteration (spec behaviour) before PDF.js loads, and `web/pdf_worker.mjs`, the worker given to PDF.js, imports it before PDF.js's worker. Also in PDF.js 6: a document has no `destroy()` any more; its loading task frees it. One `PDFWorker` serves every PDF. The result is committed; Brain Fry needs neither Node nor the network at runtime. npm's `node_modules` stays in `~/.cache/brain_fry/vendor-build`, outside SWITCHdrive.
- Commands that need an answer (files, a new shell) carry a request number on `/ctl`; the backend replies with the same number.

## Selection as context

Asked by Renaud on 2026-11-10: what VS Code does without a key. The text that I select in an editor goes with my next prompt to Claude Code, which shows "N lines selected".

- VS Code does it over its IDE connection: the extension runs a websocket server, and sends `selection_changed` (`filePath`, `selection`, `text`) to the CLI at each change. Seen in the binary of 2.1.322. Rejected for now: the protocol is internal, and its discovery and authentication were not checked. It would also bring `at_mentioned` (the key that types `@path#L51-52`) and `openDiff`.
- Brain Fry does it through its hook. The front end sends the selection of the active file tab (`selection.set` on `/ctl`, 120 ms after the last change). The backend keeps it in `~/.brain_fry/selection.json`: session id, the app's pid, path, first and last line, text, unsaved flag. At UserPromptSubmit, the hook prints it when the prompt's session id is the file's and the pid is alive. Claude Code adds that stdout to the model's context as "UserPromptSubmit hook additional context". Tested on 2026-11-10 with `claude -p` and the hook in `--settings`: the model named the file, the lines and the text.
- The text follows the CLI's own words for an IDE selection: "The user selected the lines 51 to 52 from <path>: <text> This may or may not be related to the current task." One line says "line 51". Unsaved edits add a note, because Claude reads the file from disk, where the lines may differ.
- Sent only when the selected task's session runs in the app (`pty`), the tab is a text file (not a thread, an image or a PDF), and 3a is on screen (Cmd+2): a selection that I cannot see is not sent. Only the main range of a multiple selection. A selection that ends at column 0 of a line stops at the line before, as in VS Code.
- The path is relative to the session's `cwd` (where Claude runs), or absolute for a file outside it. Paths must stay inside the project.
- At most 10,000 characters; the hook then adds "cut here: read the file for the rest".
- The selection stays until it changes, as in VS Code: every prompt to the task carries it while it is selected. CodeMirror keeps its selection when I click into 4a.
- Indicator: a chip at the top right of 4a, "⧉ 2 lines selected · x.py", with × to unselect. It lies over the terminal, because a strip above it would resize the PTY at each selection, and Claude Code would re-render.
- The file is deleted when the app starts and quits, and when the last front end disconnects. A reloaded page sends its selection, or a clear, at once. The pid check covers a crash. Sessions in VS Code or a terminal never get it: their session id differs.
- The hook in `~/.brain_fry/` must be updated (`bf install`) for this to work: the banner asks for it.
- Not built: a key that types `@path#L51-52` into 4a, as VS Code's Cmd+Option+K (the IDE message `at_mentioned`, lines 0-based; the CLI writes the path relative to its cwd and a final space). Renaud uses the selection, not the key. If wanted later, it needs no IDE connection: the CLI's @-mention parser reads `#L51` and `#L51-52` (regex `^([^#]+)(?:#L(\d+)(?:-(\d+))?)?`, seen in 2.1.322), so the front end can write the text to the PTY, as a bracketed paste so that `@` does not open the file autocomplete (not tested). For a session that runs elsewhere: the clipboard.

## Browser (3a)

Asked by Renaud on 2026-11-10: a decent browser in panel 3 that keeps its cookies and has uBlock. Built 2026-11-10. The research behind the choice of engine is under Rejected.

- Engine: the system WebKit, as a second native view. A browser tab is a tab of 3a (`kind: 'web'`, `web/browser.js`) whose element is a placeholder; the page is a WKWebView (`app/browser.py`) added to the window over the placeholder's rectangle. The page sends the rectangle at every frame and every 250 ms (`browser.place`; WebKit pauses frames while the window is covered). The view hides when its tab is not on screen (another tab or task, Cmd+2, Organize mode).
- Why not an `<iframe>`: most sites forbid framing (`X-Frame-Options`, CSP `frame-ancestors`), and WebKit blocks the cookies of an iframe from another origin as third-party, so logins fail.
- A native view always paints above Brain Fry's page. While an HTML dialog covers 3a (the project picker, the splash), the view is hidden and a snapshot of it (`browser.snapshot`, JPEG) fills the placeholder. A toast that would fall on the page moves over 4a. (For PDFs, a native view was rejected for this reason; a browser has no other way.)
- Cookies: one persistent website data store (`WKWebsiteDataStore(forIdentifier:)`, macOS 14+) for every tab of every task, so a new tab has them. Its id is a uuid5 of the Brain Fry home, so tests (`BRAIN_FRY_HOME`) have their own profile. WebKit keeps it in `~/Library/WebKit/python3/WebsiteDataStore/<id>/`, a folder named after the process: if Brain Fry becomes a `.app`, the profile must be moved. pywebview's private mode wipes the default store at each start, not this one (tested).
- Session cookies (no expiry) die with the process in WebKit, as in any browser without session restore (tested). Brain Fry saves them every 30 s and at quit to `~/.brain_fry/browser/session_cookies.json` (mode 600, its folder 700: it holds logins) and sets them back at start. Tested in the window: the first request after a restart carried both kinds of cookie.
- My Firefox cookies (`firefox.py`, asked by Renaud on 2026-11-10): copied once, at the first start of the browser (when `browser/firefox_import.json` does not exist yet), and again by "Overwrite my cookies" in the burger menu. Per site, Firefox's cookies replace the browser's: the cookies of every site that Firefox has cookies for are deleted first (WebKit's data records, one per registrable domain: `google.com`), so that two logins never mix. The sites that only Brain Fry knows keep theirs. Page loads wait during the copy (20 s at most). Open pages keep what they loaded: a reload uses the new cookies.
- What is copied: the persistent cookies of the default container of the profile that Firefox opens (the `Install` section of `profiles.ini`, else the profile whose cookies changed last). Firefox locks `cookies.sqlite` while it runs, so Brain Fry reads a copy of it and of its WAL (the latest writes, about 850 KB here), in a private temp folder deleted at once. Skipped: Firefox's session cookies (it keeps them in memory and in its compressed session store, not in `cookies.sqlite`), partitioned cookies (`^partitionKey=`), container cookies (`^userContextId=`), expired ones. Firefox 13x stores `expiry` in milliseconds (seconds before) and `sameSite` 256 for "not set". CFNetwork caps a cookie's lifetime at 400 days. Renaud's profile on 2026-11-10: 2,714 rows, 2,530 in the default container, 748 hosts.
- The burger menu (☰, next to the logo, `web/menu.js`) holds actions that I need rarely. For now one: "Overwrite my cookies", with the time and counts of the last copy. No confirmation: a click that I did not mean replaces the cookies of a site with Firefox's, where I am logged in anyway.
- uBlock Origin Lite, the Safari build of the official release (`ublock.py`). `bf ublock` downloads it, refuses it unless its SHA-256 matches the one that GitHub publishes for the asset (`digest` in the releases API), and unpacks it into `~/.brain_fry/extensions/ublock-lite/`. `bf install` runs it too; `bf ublock --zip` installs a local file. It is loaded through WebKit's extension API (`WKWebExtension`, macOS 15.4+), with all its permissions granted. Full uBlock Origin cannot run: it needs `webRequestBlocking`, which WebKit does not have (and Chrome removed in 2025); only Firefox keeps it.
- The extension needs a fixed identity (`uniqueIdentifier`, base URL `webkit-extension://ublock-lite/`), else WebKit gives it a new one at each start and its settings are lost (tested). Its own pages (popup, dashboard) work only in a view made from `context.webViewConfiguration()`.
- uBlock's rules apply about 2 s after its context loads at a start (measured on 2026-11-10: a load at +1 s showed the ads, one at +2 s did not). Page loads wait until 2.5 s after the load, so that a restored tab shown at once is filtered (tested). The first start after an update compiles the rules again (about 5 s in the spike): those seconds leak.
- Filtering mode: uBOL's default ("optimal": network rules, per-site cosmetic filters, scriptlets). Its generic cosmetic filters (ad slots hidden on any site) run only in its "complete" mode, by design. Both tested offline in a spike (deleted on 2026-11-10). WebKit applies uBOL's CSS only in a page on screen: uBOL inserts it in a `requestAnimationFrame`.
- uBlock's popup: the uBlock button of the toolbar shows uBOL's popup page in an NSPopover. WebKit loads the page but did not call the delegate `presentActionPopup` (macOS 26.7), so Brain Fry shows `action.popupWebView()` itself.
- Toolbar (the bar of 3a): back, forward, reload / stop, address (a URL, a host, `localhost:5173`, or words: a Google search), find (Cmd+F; Enter, Shift+Enter, Esc), uBlock. A tab is named after its page's title; its tooltip is the URL. "+ Browser" at the end of 3a's tabs, or Cmd+T, opens a tab with the address field focused.
- Keys: a key monitor (`NSEvent` local monitor) sees each key before WebKit. While a page has the focus, Brain Fry's Cmd keys (Cmd+Up/Down, D, E, Shift+D, N, P, B, 1, 2, J) and the browser's keys that live in Brain Fry's page (Cmd+L, T, W, F) go to the page (`browser` message `key`, dispatched as a keydown). Cmd+R, Cmd+[ / ] and Cmd+= / - / 0 (zoom) act on the page directly. The rest (copy, paste, undo) stays with the page. Cmd+W closes the browser tab on screen, also when the focus is in Brain Fry's page; without a browser tab on screen, it keeps pywebview's meaning (close the window).
- Focus: a tab that I open or click gets the keyboard at its next placement (`browser.place` with `focus`). A view that hides gives the keyboard back to Brain Fry's page.
- `window.open`, `target=_blank` and Cmd+click on a link open a tab of the same task (Cmd+click: in the background). A popup's view is made with the configuration that WebKit passes, so `window.opener` works (OAuth logins). `window.close()` closes the tab. Links with another scheme (`mailto:`, `zoommtg:`) go to their app.
- Closing a tab ends its page. Found by Renaud on 2026-11-10: a closed YouTube tab kept its sound. Removing the view from the window is not enough while something holds it, and the tab held itself: page --> its WebKit extension tab --> page, a cycle through an Objective-C object that PyObjC cannot collect. The close now pauses the media, closes fullscreen and picture in picture, cuts the cycle, and closes the page (`_close`, WebKit SPI). Tested in `host_check.py`: with a view still held, the old steps left a looping sound playing, the new close stops it. A hidden tab (another tab or task) plays on, as a background tab in any browser.
- Downloads (`Content-Disposition: attachment`, a type that WebKit cannot show, `<a download>`) go to `~/Downloads` under a free name (`a (1).pdf`), with a toast "Show in Finder". JS alert, confirm, prompt and file pickers are native panels. Right click --> Inspect Element, and Safari's Web Inspector, work in the pages.
- Per task: the URLs of a task's browser tabs are saved in its task file (`browser_tabs`). When the task is selected for the first time after a start, the tabs come back, and each loads its page when it is first shown. A task without file tabs shows its first browser tab.
- Links in the terminals: Cmd+click on a URL in 4a or 3b opens it in a browser tab of the task, as in VS Code's terminal (a plain click selects text). Also for OSC 8 links. A URL that wraps onto the next line is cut at the line end.
- The user agent ends with Safari's `Version/<macOS> Safari/605.1.15`, so sites treat the pages as Safari.
- Not logged: the URLs (browsing history). Changes of `browser_tabs` are logged as counts (`browser_tabs 1 -> 2`); until 2026-11-10 they were logged with their URLs. bf.log has the tabs opened and closed, uBlock's load, the session cookies restored and saved, and each copy of the Firefox cookies (counts and profile).
- PyObjC: the Objective-C classes of `browser.py` implement WebKit's protocols without `protocols=[...]`. With it, PyObjC takes the signatures from the runtime protocol, which does not describe blocks, and calling a `decisionHandler` crashed the app ("cannot call block without a signature"). The protocols are added afterwards through the runtime. PyObjC 13's metadata lacks `presentActionPopup`: registered by hand.
- Tests: `tests/test_browser.py` (installer, task field, backend commands, helpers). `spikes/browser/host_check.py` runs `BrowserHost` in a real window against a local site (`site.py`): placement, keys, popups, `window.close()`, a download, uBlock's popup, session cookies, the sound of a closed tab, the copy of Firefox cookies from a fake profile (32/32 on 2026-11-10). `bf --selftest` draws the browser views into its screenshot.
- Not tested yet: Google sign-in (Google blocks embedded browsers and forbids faking the user agent; saved cookies may still keep me logged in), real sites with uBlock (the tests use only the local site: no network), trackpad gestures (swipe back and forward, pinch), fullscreen video, dragging the splitters by hand.
- Not built: password autofill (macOS Passwords does not fill in another app's web view), passkeys (they need an Apple entitlement that a Python app cannot get), other extensions, bookmarks, a history view, private tabs.

Both are required: an agent that asks something back before closing goes to the inbox, and the mark alone (without my prompt) archives nothing. The thread stays `pending`, so the digest still runs. As with my key, the process keeps running, and a new prompt in the session brings the task back from the archive. Code: `events.closes`.
- Inside a column, cards are sorted by last update. A card shows the status color, the project label, then the short title (the title until the task has one; the title in its tooltip), then the task's digest, cut to 4 lines (all of it in its tooltip), and, while the task is in the inbox, its inbox line under a rule. ## Reply trailer and resume note (not built), auto-advance

Three additions from a review on 2026-11-09. It compared the design with my Claude Code transcripts (296 sessions, 1,217 prompts, 2026-08-27 to 11-09) and with research on interruptions and on supervising automation. The analysis and its sources are in RESEARCH.md.

Status on 2026-11-10: auto-advance is built. The reply trailer and the resume note are specified but not built: no code parses `[needs: ...]`, the hook has no SessionStart handler, `bf install` writes no `trailer_prompt.md`, and nothing asks for a resume note. The text below describes how they will work.

**Reply trailer (not built): the agent says what it needs from me**

- Every reply of an agent ends with one line: `[needs: KIND] TEXT`. KIND is a thread kind:
  - `answer`: the agent asked me a question. TEXT is the question.
  - `rule`: I must choose between options or rule on a trade-off. TEXT names the choice and its options.
  - `review`: the agent changed something that I should check. TEXT says what to check and where.
  - `fyi`: nothing is needed from me. TEXT is the outcome in a few words.

  When several apply, the first in this order wins. `blocked` still comes from the Notification hook.
- Why: the agent has the whole context of its turn, while Sonnet infers the kind from a reply cut to 8,000 characters. The line also shows in 4a, at the end of the reply. In the transcripts, only 13% of final replies had a question in their last paragraph, so most trailers will say `review` or `fyi`.
- The instruction is `~/.brain_fry/trailer_prompt.md`, written by `bf install`. The hook prints it on SessionStart, and Claude Code adds the stdout of a SessionStart hook to the model's context (documented; it does not show as a message in the terminal). SessionStart fires on startup, resume, clear, compact and fork, so the instruction comes back after a compaction. This reaches every session in a Brain Fry project, wherever it was started (Brain Fry, VS Code, a plain terminal), and changes no CLAUDE.md. On SessionStart the hook writes no event file.
- Not `--append-system-prompt`: it reaches only the sessions that Brain Fry starts. And Claude Code records the system prompt at a conversation's first request and resends that record until a compaction (`--system-prompt-snapshot`, on by default), so an edit of the text would not reach the existing sessions.
- The hook prints nothing for scripted `-p` runs, because a script may parse their output: it skips when `CLAUDE_CODE_ENTRYPOINT` is `sdk-cli`.
- At Stop, Brain Fry reads the last non-empty line of `last_assistant_message`. It accepts `[needs: KIND] TEXT` in any case, also inside `*` or backticks. No such line, or an unknown KIND: no trailer, and the kind comes from Sonnet as before.
- With a trailer, the thread gets its kind and question at once, and the inbox row shows the trailer instead of the start of the reply. Sonnet still writes the title and the digest; its prompt says that the trailer is the agent's own claim. When Sonnet's kind differs, the thread keeps it as `**Sonnet kind**` and the inbox row shows a small mark. These disagreements show how far each label can be trusted. That matters: research on diagnostic aids finds that a label that is right less than about 70% of the time does worse than no label (Wickens & Dixon 2007).
- The reply in the task file stays verbatim, trailer included.
- First text of `trailer_prompt.md`:

```
End every reply with one last line, and nothing after it:
[needs: KIND] TEXT
KIND is one of:
- answer: you asked me a question. TEXT is the question, in one sentence.
- rule: I must choose between options or rule on a trade-off. TEXT names the choice and its options.
- review: you changed something that I should check. TEXT says what to check and where.
- fyi: you need nothing from me. TEXT is the outcome in a few words.
If several apply, use the first in this list. If you have several questions, TEXT holds the most important one and the others go in the reply above.
```

**Resume note (not built): one line from me when I leave a task unfinished**

- When I dismiss a task, or move it into a hidden column (later, more later, never), a one-line input opens and takes the focus: on the task's row in 1a (Dev mode), or on its card (Organize mode). Enter saves. Esc closes it without saving. Up/Down, Cmd+Up/Down, a click on another task or a mode switch close it and save what I typed. So an FYI item costs no extra key: Cmd+D, then Cmd+Down, as before.
- While the input is open, letters and Left/Right go to it, not to the Organize keys.
- No input on archive (the task is done), on answer (the agent continues and will reply), or on a move between working and planning (the task stays in view).
- I write the note; nothing is prefilled. Why: Leroy & Glomb 2018 found that a short plan, written when leaving an unfinished task (where I stopped, what is left), reduced the attention that stays on it and improved the next task. Dismiss alone records no plan, and the digest is Sonnet's summary of the past, not my plan.
- The note is saved as `resume_note` in the frontmatter. It shows on the card, under the digest in the inbox row when the task comes back, and in the header while the task is selected. My next prompt to the task (UserPromptSubmit) removes it. Each note is also logged in `events.jsonl`, so that I can see later how often I write one and whether the habit lasts.

**Auto-advance: after I answer, the next item**

- When I send a prompt to the selected task in Dev mode, Brain Fry selects the next inbox item about 1 s later. The trigger is that task's UserPromptSubmit event; the second lets me see that the prompt was accepted.
- The task that I answered leaves 1a at the advance (Renaud, 2026-11-10: "it should disappear"). Cmd+Up from the first inbox item selects it again: to watch it, or to press Esc when the agent goes the wrong way. It comes back in the inbox when its agent replies.
- No advance when nothing else in the inbox needs me (pinned tasks without a reply or a block are skipped): 4a keeps the task. No advance for a prompt that starts with `/` (`/model` or `/compact` is not an answer); the payload's `prompt` field gives the text. Granting or refusing a permission, or answering a question of the agent, advances too, but later: the scan of Claude Code's process files sees it within 3 s, then the advance waits its second (see Hooks, "Red clears"). The `prompted` message then has `why: dialog closed`.
- No advance either when I typed in the task's terminal after its prompt arrived (a follow-up that I am typing would otherwise land in the next task's terminal), or when I selected another task within the second.
- A switch in the header turns auto-advance off. The window remembers it (localStorage).
- Archive (the button or Cmd+E) of the selected task in Dev mode advances at once, with no second to wait, and also when the switch is off: the task is done, so there is no agent to watch (Renaud, 2026-11-10: "remove it from inbox and move to next one"). The next item is chosen as after an answer (the item after it in the inbox order, pinned tasks that need nothing skipped). The archived task leaves 1a at once. When nothing else needs me, nothing is selected and 4a says so. Cmd+Up from the first item goes back to the archived task, to unarchive it. Unarchive and the archive of Organize mode (E on a card) do not advance. Tested on 2026-11-10 with a sandbox selftest: inbox C, B, A; archive B --> A, Cmd+E in 4a's textarea --> C, archive C --> empty, Cmd+Up --> C.
- Cmd+E and not Cmd+R (Renaud proposed Cmd+R on 2026-11-10; Cmd+A is select all): Cmd+R reloads the page of a browser tab of 3a, and E matches the E of Organize mode.
- How: when the backend applies a UserPromptSubmit, it sends a `prompted` message on `/ctl` (task id, and whether the prompt starts with `/`), before the state push. The front end takes the inbox item that came after the task in the inbox order at that moment, else the first one. It logs each advance, and each advance that it skipped with the reason, in bf.log (logger `brain_fry.ui`). Tested on 2026-11-10 in the window: inbox C, B, A; an answer to B selected A 1.0 s later.
- Why: after an answer, 4a shows the agent at work for a median of 2 min (agent turn, in the transcripts). That moment invites three things:
  - watching the agent: tools that need constant monitoring were the strongest predictor of fatigue in the BCG survey (Bedard et al., HBR 2026; a survey, so an association, not a proven cause);
  - choosing the next item: a small decision, about 20 times a day;
  - starting a new session to fill the wait: the spiral of brain_fry.md, which ParallelPilot and METR also observed.

  Auto-advance removes that moment. It makes the switch that I already make on 75% of my prompts.
- Not for speed: in the transcripts a switch cost no measurable time (median 205 s to answer a waiting reply after a switch, 217 s after staying). It can backfire: a faster flow pushes more items through me per hour. The weekly measures of idea 10 in RESEARCH.md would show that.
- Watching is rarely needed: 15 interrupts in 1,198 turns. A permission prompt needs no watching, because the task comes back red and sorts first.

## Worktrees (discussed 2026-11-10, not built)

Renaud asked whether a task should get a git worktree by default. Decision: write it down, do not build it now.

- Today no task gets a worktree. A new task runs `claude --session-id` in the project root (`actions.new_task`), a fork in its parent's `cwd` (`actions.fork_task`), a resume in the task's `cwd`. That `cwd` is set when the task is born and never updated from later events (`events.py`). The only support is passive: the hook walks up from `cwd`, so a session that Renaud starts with `claude -w` (Claude Code 2.1.322 creates `.claude/worktrees/<name>/`) still lands in its project. `.claude` is in `~/.gitignore_global`, so worktrees there are ignored by git; `.brain_fry/` is too, so a worktree holds no `.brain_fry/` and the walk-up reaches the project's.
- For: isolation (an agent does not see another agent's half-finished edits, its tests do not fail on them); a diff per task (in a worktree, "Diff vs HEAD" shows only this task's work, which v2's review needs); closing a task = merging its branch and removing its worktree, the "close it" step of brain_fry.md.
- Against a default for every task:
  - A worktree starts from HEAD, not from the working tree. On 2026-11-10 this repo had 1 commit, 28 modified files and 17 untracked ones: a worktree task would not have seen the day's work. A default would force a commit before each task, against Renaud's way of prototyping.
  - Gitignored files are missing in a worktree: `.venv` (uv rebuilds it), `.env`, data folders, checkpoints. In an ML project the agent may not find its data.
  - Many tasks write no code (quick questions, research). At 7.6 new sessions per active day, worktrees and branches pile up, and each task that writes adds a merge. Conflicts move from silent and continuous (one shared folder) to explicit at merge time: one more decision in the inbox.
  - Some projects may not be git repos.
  - SWITCHdrive syncs `.claude/` (its exclude list has only `.venv`, `node_modules`, `target`, `*_nosync`), so each worktree is uploaded (about 9 MB of tracked files for this repo). A `*_nosync` folder avoids it, but uncommitted work in it would have no backup. Minor for code repos.
- Renaud's `land` instruction (`~/.claude/CLAUDE.md`) already describes an opt-in habit: a worktree when another agent works in the main tree.
- Evidence still missing: the 67% of RESEARCH.md (two concurrent agents shared a project folder) measures how often the risk was present, not how often harm happened. Default worktrees cost something on every task, so they pay off only if collisions are frequent. Proposed count, from the transcripts that the scan of other sessions reads: Edit and Write tool calls carry a file path and a timestamp; count the cases where two sessions of one project edited the same file within about 30 minutes, and the turns where a test run failed while another session was editing. A proxy: it misses conflicts that span files and counts harmless overlaps, but it is much closer to harm than sharing a folder. Around 1 turn in 200: worktrees would solve a rare problem at a daily cost. Around 1 in 10: a default is justified.
- Two questions for Renaud decide it: how often do two agents that write code run in one repo at once, and is he willing to commit before starting such a task?
- If built:
  - Opt-in: a modifier in the Cmd+N picker (e.g. Option+Enter) for "new task in a worktree", and `"worktree": true` per project in `projects.json` for a project default.
  - Brain Fry creates the worktree itself (`git worktree add .claude/worktrees/<id> -b bf/<id>`) and starts `claude --session-id` there, rather than passing `-w`: as with `--session-id`, it knows the path from the start, and `--resume` must run there.
  - 2a and "Diff vs HEAD" follow the task's `cwd`, not the project root.
  - Archive: a clean worktree whose branch is merged is removed with its branch; otherwise Brain Fry asks (merge, keep, discard). Renaud's `land` steps become a Brain Fry action.
  - Open: what a fork of a worktree task gets (the parent's worktree, or a new one from the parent's branch, which needs a commit).
  - Middle path: every task starts in the main tree and moves into a worktree once it starts writing (Claude Code's EnterWorktree tool does that during a session). Brain Fry would then have to update the task's `cwd` from the hook events.

## Rejected

- For PDFs (2026-11-10): WebKit's own PDF viewer in an `<iframe>` (unknown whether WKWebView in pywebview shows it; a reload would go back to page 1, because the page cannot read the plugin's position; the plugin may take Brain Fry's keys while it has the focus), and a native PDFKit view laid over the web view (a native layout under a web layout; the selftest snapshots would not show it). For the bytes of images and PDFs: base64 over `/ctl` (a third larger, and a big PDF would hold up the state and the commands).

- For the browser of 3a (researched on 2026-11-10). Renaud's Firefox inside the window: macOS cannot put another app's window inside a window, Gecko embeds only on Android, and Servo (Rust API since April 2026) has no Python bindings and fails logins (Gmail with two-factor). Streaming a Firefox window into the panel: Firefox's remote protocol gives screenshots, not a stream; ScreenCaptureKit plus forwarded input needs two permissions and handles input badly. Firefox beside Brain Fry, and an `<iframe>`: Renaud, "not an option". Chromium through Qt WebEngine: the whole app would move to pywebview's Qt backend, for the same Manifest V3 uBlock Lite. Chromium through CEF: cefpython's Mac build is a pre-release, "tested in CI only" (2026-11-03).

- sqlite: tasks are markdown files, the app is a viewer over them.
- Sonnet through the API: needs a key and billing. `claude -p` uses the subscription.
- A TUI (Textual + tmux), the first design. Textual has no mature terminal widget (checked 2026-11-09: textual-tty 0.4.0 is pre-alpha and has no scrollback, textual-terminal is unmaintained since June 2024, Toad's shell is not a separate package). And tmux panes are rectangles, so 3b could not sit under 3a.
- Native Swift + SwiftTerm: the lightest and most Mac-like option. But the whole app would be in Swift, there is no known track record of Claude Code in SwiftTerm, the editor and diff components are weaker, and Claude can test a native window less easily.
- Electron: ships Chromium, not lightweight. Tauri: the backend would be in Rust.
- tmux as the host of the sessions, under the GUI: sessions would survive the app, but the scrollback would live in tmux, not in xterm.js.
- A separate inbox-triage agent session: 4a is the selected task's own session.
- A done column.
- A list of all tasks in Dev mode: the board does that.
- Notifications.
