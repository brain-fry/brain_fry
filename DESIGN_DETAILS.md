# Design details

Decisions and rationale behind DESIGN.md (Renaud's spec and the core). One section per area: read the section of the area that you work on before you change it. Settled items are stated as facts. Items that still need a decision or a test are in "Still open". Facts about Claude Code were checked against the docs on 2026-11-09.

## Naming and files

- "Brain Fry" in prose, `brain_fry` in code, folders and the package name. `bf` is the command.
- Global, in `~/.brain_fry/` (`BRAIN_FRY_HOME` moves it): `projects.json` (projects and views), `inbox_prompt.md`, the hook script, `extensions/ublock-lite/`, `browser/session_cookies.json` and `browser/firefox_import.json` (see Browser).
- Per project, in `<project>/.brain_fry/`: one task file per session, `<session-id>.md`; `events/`, the spool (one file per hook event, written by the hook, deleted by Brain Fry once applied); `events.jsonl`, the log of applied events (written by Brain Fry only). `consume.lock`: the reader holds it (flock) while it applies the spool, so that `bf list` or `bf consume`, run by hand while the app runs, cannot apply an event twice.
- Why a spool and not one file that the hook appends to: jq may write a long line in several `write` calls, so two hooks that end at the same moment could interleave their lines. And consuming an append-only file needs a saved offset or a rotation, both racy while hooks append. A temp file plus a rename avoids both.
- Task files are not committed. Add `.brain_fry/` to `~/.gitignore_global`. A project that wants them committed negates the rule in its own `.gitignore`.
- `bf init` in a project creates `.brain_fry/` and registers the project in `projects.json`, so the hook condition (folder exists) and the project list never disagree.
- `bf install`, once per machine: adds the hook entries to `~/.claude/settings.json` next to the existing ones (8 events already have hooks there: carbon, statusbar). Safe to run twice, keeps a backup. Adds `.brain_fry/` to `~/.gitignore_global`. Writes a first `inbox_prompt.md`, and installs uBlock Origin Lite (see Browser). Planned with the reply trailer: `trailer_prompt.md`.

## Task file

YAML frontmatter, then the rolling digest, then one section per thread (TT).

- Frontmatter: `session_ids` (a fork gets its own file, see Split), `title`, `short_title` (2 or 3 words, the heading of the card, see Status, inbox, board), `cwd` (where the session started: `--resume` must run there), `transcript_path`, `project`, `prio` (working, planning, later, more_later, never), `status` (working, blocked, waiting, done), `live`, `inbox`, `unread`, `held` (a reply that waits for the digest's verdict, see Hooks, "Background work"), `parent` (the task that this one was forked from), `resume_note` (planned, see Resume note), `created`, `updated`, `opened` (last selected in Dev mode, see Project dropdown), `open_files`, `terminal_tabs`, `browser_tabs` (URLs, see Browser).
- Thread section: timestamp, kind (review, answer, rule, FYI, wait, blocked), digest, the question verbatim if there is one.
- Layout: `# Notes` (only when the task has notes: see Modes, a new task in Organize mode; the other files stay as they were), `# Digest`, then `# Threads` with one `## n | timestamp | kind` section per thread, with the parts `**Digest**`, `**Question**`, `**Prompt**`, `**Reply**`, and, once the reply trailer is built, `**Sonnet kind**` when Sonnet disagrees with it. All free text is written as blockquote lines (`> ...`), so no content can be mistaken for structure, whatever headings, fences or `---` lines it holds. The parser reads only the lines without `>` as structure.
- A thread is born at UserPromptSubmit (kind `working`, with the prompt). Stop adds `last_assistant_message` as the reply and sets the kind `pending` (planned: the kind of its trailer, when it has one); the digest then sets the final kind. A new prompt before any Stop (Esc) marks the previous thread `interrupted`. A Stop without a prompt before it (a background task that finishes, or hooks installed mid-session) makes a thread without a prompt.
- The task file keeps the prompt and the full reply of every thread: the digest needs them, and the transcript may be gone after 30 days.
- Until the first digest, a task shows the first line of its first prompt as its title.
- The task file is the record. Claude Code transcripts are deleted after 30 days by default, and their JSONL format is documented as internal. A task must hold everything that Brain Fry needs; the transcript is read as little as possible.
- Per-task workspace: open file tabs, browser tabs and terminal tabs (the panes of column 3) belong to the task and are restored when the task is selected. The explorer root (2a) is the task's project.

## Hooks

Source: https://code.claude.com/docs/en/hooks.md

- Stop fires every time Claude finishes a turn and waits for input. It does not fire on a user interrupt (Esc). SessionEnd fires when the CLI exits. The inbox trigger is Stop, not SessionEnd.
- Notification fires with `notification_type` `permission_prompt`, `idle_prompt`, `elicitation_dialog` (and others) when Claude is stuck waiting, after about 6 seconds without typing. That is the blocked case.
- Every payload has `session_id`, `transcript_path`, `cwd`, `hook_event_name`. Stop adds `last_assistant_message` (use it: the transcript may not yet contain the final message). Notification adds `message` and `notification_type`. Session id = task id. The project comes from cwd, see the walk-up below.
- Hooks run synchronously, Claude waits for them. Default timeout is 600 s for command hooks.
- Registered once in `~/.claude/settings.json`, so they run in every project. Events used: UserPromptSubmit, Stop, Notification, SessionEnd. SessionStart is planned, to print the trailer instruction (see Reply trailer).
- The hook is bash plus jq, not `uv run`, because it runs at every turn end. It exits at once when `BRAIN_FRY_INTERNAL` is set. Otherwise it walks up from `$cwd` to the nearest folder that has `.brain_fry/`, and exits if there is none. The walk stops below `$HOME`, because `~/.brain_fry/` is the global folder, not a project. It writes the payload, plus `bf_ts` (epoch seconds, from jq's `now`) and `bf_project`, as one file in that folder's `.brain_fry/events/`. It prints nothing, except my editor selection on UserPromptSubmit (see Selection as context): on UserPromptSubmit and SessionStart, stdout is injected into Claude's context.
- Walking up, and not only checking `$cwd`, keeps the sessions that start in a subfolder or in a worktree under `.claude/worktrees/`. For nested projects, the nearest folder wins.
- Hook processes inherit the environment of the `claude` process (documented). That is what makes the `BRAIN_FRY_INTERNAL` guard work.
- Seen on 2026-11-09 (Claude Code 2.1.318): the Stop payload also has `prompt_id`, `background_tasks`, `permission_mode`, `effort`, `session_crons`, `stop_hook_active`. At the end of a `-p` run, SessionEnd has `reason: other`. Tested end to end with `claude -p --settings` that adds the hook: an event from a subfolder lands in the project's spool.
- `claude --resume <id>` keeps the session id and appends to the same transcript. `--fork-session` gives a new id with the full history. Resuming one id in two terminals interleaves both into one transcript.

Event --> status:

| event | status | color |
|---|---|---|
| UserPromptSubmit | working | orange |
| Notification permission_prompt, elicitation_dialog | blocked | red |
| the dialog closes (no hook: Claude Code's process file, see below) | working, or waiting after a refusal. `inbox` off | orange |
| Stop | waiting (needs me) | green |
| Stop while background agents or workflows run | working, `inbox` off (not done yet) | orange |
| Stop while a background shell or monitor runs | working, `inbox` off, `held` until the digest: kind `wait` keeps it so; any other kind, or a failed digest --> waiting, `inbox` and `unread` on | orange, then orange or green |
| SessionEnd | unchanged, but working or blocked --> waiting (nothing runs any more), `inbox` and `unread` on (the turn was cut off). `live` off | unchanged, or green |
| archive (my action) | done | gray |
| Stop of my `close` (or `x`) prompt, reply with `closed :-)` | done (archived), `inbox` off | gray |

- A task started from Brain Fry is born at once: `bf` runs `claude --session-id <uuid>`, so it knows the id before the first hook. Prio working, status waiting, `inbox` off. A session started elsewhere is born at its first UserPromptSubmit, Stop or Notification; SessionEnd alone creates no task. When its project was registered in the middle of the session, its earlier turns are imported from its transcript as `imported` threads (Renaud, 2026-11-10), and so does a session that started before `bf install` and is resumed since. The event's own turn is found by `prompt_id`, which is the `promptId` of its prompt in the transcript (checked on 2026-11-10), else by the prompt's text. A first Stop whose `prompt_id` is not the last prompt's (a background task) gets a thread of its own. Sessions with no `.brain_fry/` in `$cwd` or a parent are ignored. Quick questions and scripted `-p` runs inside a project do create tasks; archive them with one key.
- Background work (Renaud, 2026-11-10: "When the agent is still working in the background, it gives me a little message saying, 'Hey it's still working,' and then it pops into my inbox. I don't want it to pop into the inbox if it's not done."). A turn ends while background agents run: Claude Code shows "Waiting for 1 background agent to finish" and fires Stop. The Stop's `background_tasks` (one entry per task in flight: `id`, `type`, `status` `running` or `pending`, `description`, plus `agent_type` or `command`) is there to tell "session is done" from "session is paused waiting for background work to wake it" (its description in the binary of 2.1.322). When it holds an agent or a workflow, the task stays working (orange) and out of the inbox; the reply is kept in its thread, `pending`, and digested as usual. Each result comes back as a turn that Claude Code starts with a UserPromptSubmit whose prompt is `<agent-message from="<agent id>">` (a subagent) or `<task-notification>` (a shell): seen in events.jsonl, 2026-11-09 and 10. That turn is a thread of its own, and its Stop goes to the inbox once nothing holds it. Code: `events.background_work`.
  - Agents and workflows only, as Claude Code's own "Waiting for N background agents and M dynamic workflows to finish" (it counts `pendingBackgroundAgentCount` and `pendingWorkflowCount`). A background shell or a monitor may never end (a dev server, a watch) and would hold its task out of the inbox for ever, so it does not hold its task by itself: the digest decides (next bullet).
  - A waiting agent out of the inbox (Renaud, 2026-11-11, on a reply of task `336ef1ec` that said "I'm waiting, and I'll be notified when the cleanup task stops working": "It's basically waiting and there's even the flag FYI. I don't need these tasks to show in my box."). A Stop whose `background_tasks` holds a shell, a monitor or an unknown type in flight, and no agent, is `held`: working (orange), out of the inbox, until the digest of its reply. The digest has a sixth kind, `wait`: Claude waits for something other than me and will go on by itself. `wait` keeps the task working and out of the inbox; any other kind puts it in the inbox (waiting, `unread`), as the Stop would have done. A failed digest puts it in the inbox too: a reply never waits for a digest that does not come. The next UserPromptSubmit, blocking Notification, Stop or session end clears `held`; an archive in the meantime stays (`actions.settle_hold`). The shell's result starts the next turn (`<task-notification>`), whose Stop goes to the inbox once nothing holds it.
    - Why not all FYI replies, as Renaud's words said: on 2026-11-11, 74 of the 211 digested threads were FYI. Most were `close` turns (archived anyway), but some answered my own questions ("What do you mean by a pin key?", "would it be a good idea to start with Theia", "how many lines of code"), which I want to read. The two replies that only said "I'm waiting" (`336ef1ec` and `d28fea7d`) both had a background shell in flight at their Stop.
    - Why both conditions, the shell and the kind: a shell alone may be a dev server (5 Stops with a monitor of an artifact's live updates had replies that needed me); the kind alone may be Sonnet's mistake on "I wait for your answer", and without anything in flight nothing can wake the agent. `wait` without a hold changes nothing.
    - Cost: a reply with a shell in flight reaches the inbox about 5 s later (the digest's time); 7 of 201 Stops had one (events.jsonl of all projects, 2026-11-11). A shell that never wakes the agent (a wait loop with a bug) keeps the task orange; the idle close after 4 h ends the session, and the task then goes to the inbox ("Turn cut off"). Crons (`session_crons`) do not count as something in flight: none seen yet.
    - The trailer (not built) would give the kind at once, without the 5 s.
  - The type test is `workflow`, or a type that contains `agent` (the hook's label is `subagent`; other agent kinds fall back to their raw name). An unknown type, or a status other than running or pending, goes to the inbox: a wrong guess then costs one inbox item, not a reply that never shows.
  - SessionEnd while the task waits for its agents: as for any working task, waiting (green) and in the inbox (see "Turn cut off" below). The agents died with the session, so their results will never start a turn: only my "Continue" restarts it. Until 2026-11-10 it stayed out of the inbox, because the last reply only said that it would wait.
  - An agent that hangs keeps its task orange: the stale orange (not built) is the cure.
- Turn cut off (Renaud, 2026-11-10, after asking whether restarting the app to load new code is that bad): when the `claude` of a working or blocked task ends, the task goes to the inbox (`inbox` and `unread` on, status waiting, the last thread `interrupted` when no reply came). Its row says `interrupted: <prompt>`, or shows the reply when one came (background agents). I resume it from there: select it, "Continue". Before, it only turned green, and my prompt had cleared `inbox`, so it left my sight at every restart. One rule, `actions.end_session`, for every way a session ends: the SessionEnd hook, the app's quit (`set_live` right after the kill: the hook's SessionEnd is applied only at the next start and then changes nothing), the leftovers of a crash (`owned.json`), the idle sweep, and the process list for sessions outside the app. A session that I end myself in the middle of a turn (Ctrl-C twice) goes to the inbox too. A session that ends while idle stays where it was.
  - Is a restart in the middle of a turn bad? Not much. On 2026-11-10 (until 17:30), 6 restarts ended 44 sessions, and 2 of them were in a turn (counted from events.jsonl: a UserPromptSubmit with no Stop before the SessionEnd). The conversation survives: Claude Code appends each message to the transcript, and `--resume` brings back everything up to the kill. Lost: the reply being written and the tool call in flight. The real risk: the app sends SIGHUP to the process group (`ptys.py`), so a command that the agent runs dies with it (a git rebase or merge left in progress, a stale `index.lock`, a half-written file), and the resumed agent does not know how far it got. Background agents and workflows die too. SessionEnd fires on that SIGHUP, with `reason: other` (seen in events.jsonl).
  - Rejected for now: keeping the `claude` processes alive across a restart (a detached PTY holder such as dtach or tmux, reattached at start). It would remove the cut, but changes how the app owns its PTYs.
- Stale orange: Stop does not fire on interrupt. If a task is working and its transcript has not changed for a few minutes, show it as stale.
- Red clears when the dialog closes: I granted or refused the permission, or answered the question. No hook fires for that (PreToolUse and PostToolUse would fire on every tool call in every project). Claude Code's process file (`~/.claude/sessions/<pid>.json`, see Claude Code's process files and transcripts) has `status` `waiting` while a dialog waits for me, with `waitingFor` (seen in the binary of 2.1.322: `input needed`, `dialog open`, a worker or sandbox request, or the dialog's own label), and `statusUpdatedAt` (ms). The scan every 3 s ends the block when a blocked task's process is `busy` (working) or `idle` (a refusal ended the turn: waiting), with a `statusUpdatedAt` after the Notification. That check rejects a snapshot of the files from before the block: the dialog opens about 6 s before the Notification fires. The task leaves the inbox, as after an answer, and the front end advances (see Auto-advance).
- Found on 2026-11-10 (Renaud: "I clicked on the right permission but the task did not disappear"): before this, red cleared only at Stop, so a granted task stayed red in the inbox for the rest of the turn. In that case the dialog was an AskUserQuestion, which also fires `permission_prompt`.
- Without Claude Code's process files (the folder is missing, or untrusted), red clears at Stop, as before.
- How to check an internal format of Claude Code: the binary (`readlink -f "$(which claude)"`, 320 MB) holds its JS source. A Python `mmap` scan for a key (here `statusUpdatedAt`, then `status:"waiting"`) prints the code around it in seconds. `grep -E` with a context pattern did not finish in 120 s, and ugrep refused it (complexity limit). Also fast: `LC_ALL=C /usr/bin/grep -a -b -o 'key'` for the offsets, then `dd` around each one. Minified names repeat across chunks: search for a literal string, not a function name.
- To see what Claude Code writes to a terminal (used for its links on 2026-11-10): a Python script that runs `claude "<prompt>" --model haiku --settings '{"disableAllHooks": true}'` in a PTY (`os.openpty`, `TIOCSWINSZ`, the variables of `CHILD_ENV_DROP` removed, `BRAIN_FRY_INTERNAL=1`, a scratch folder) and saves the raw bytes. Three traps: the prompt must come before `--allowedTools`, which takes several values and swallows it; the trust dialog of a new folder starts on "No, exit" (send Down, then Enter); at start Claude Code sends OSC 11, DA1 (`ESC[c`), XTVERSION, the kitty keyboard query and OSC 7501 (the probe answered OSC 11 and DA1, as xterm.js does).
- Sessions started outside Brain Fry (plain `claude` in a terminal) fire hooks and appear on the board, but have no terminal in Brain Fry. They are read-only until SessionEnd, then resumable. Brain Fry also reads Claude Code's list of running processes, so it knows where they run, and when they end even without a hook (see Claude Code's process files and transcripts).

## Digest (Sonnet via claude -p)

- Input, rolling: the task's current digest plus the last thread (the user prompt and `last_assistant_message`, tool calls reduced to tool names and file paths, tool outputs dropped). Bounded cost; has goal, question and answer. Weakness: summary errors compound over many turns. Accepted.
- Output, fixed structure through `--json-schema`: title, short title (2 or 3 words), digest of three to five lines, kind (review, answer, rule, FYI, wait, blocked), question verbatim or null. `wait` (added 2026-11-11) is also described in the schema, so that an `inbox_prompt.md` older than it still gets it; see Hooks, "Background work". The kind field is what makes the inbox an owner inbox and not a notification list. Planned: when the reply has a trailer, the trailer's kind wins (see Reply trailer).
- One Stop = one turn = one thread. Normally one digest call per turn. The backlog at startup is batched: one call per task covers all of its turns that were not digested yet, and still returns one thread section per turn.
- Title: the first digest sets it, later digests do not change it (a card title that changes every turn is hard to follow). The UI has no way to rename a task since 2026-11-10: the only one was a double-click on the title in the header, which was removed (see Status, inbox, board). The `rename` command of the backend stays.
- Short title: set once, as the title. A rename sets both, so that my name shows on the card, whatever its length. When Sonnet returns none, the first three words of the title stand in, so that a task never loops on calls for it. The schema describes the field too, so an `inbox_prompt.md` from before the field still gets one.
- Tasks from before the short title (added 2026-11-10): the sweep queues a call for each task that has a digest and turns but no short title. The call sends no turns, and only the short title is applied: title, digest and threads stay. Tried on 4 tasks: "Cmd+N project picker ranked by recent use" --> "Project picker". The digest queue has two priorities, so that these calls (about 25 at the first start) never delay the digest of a turn. A fork without a turn of its own is skipped: a short title made from its parent's digest would name the parent's topic.

```
BRAIN_FRY_INTERNAL=1 claude -p --model sonnet \
  --output-format json --json-schema "$SCHEMA" \
  --no-session-persistence \
  --settings '{"disableAllHooks": true}' \
  "$PROMPT"
```

- Recursion guard: the digest call is itself a Claude Code session and would fire the Stop hook. Primary guard is the `BRAIN_FRY_INTERNAL` variable. `disableAllHooks` is a second layer: the docs say that it overrides project settings and imply that it overrides user settings.
- `--bare` would skip hooks and CLAUDE.md, but in bare mode Claude Code does not read the OAuth login and needs an API key. Not usable with the subscription.
- Without `--bare`, every digest call loads `~/.claude/CLAUDE.md`. Accepted. Running the call with cwd `~/.brain_fry/` avoids at least the project's CLAUDE.md.
- `--no-session-persistence`: no transcript for digest calls. `-p` sessions are hidden from the picker and from `--continue` anyway.
- `structured_output` is missing from the JSON when the run failed. Check before reading.
- Red items get no Sonnet call. The inbox shows "blocked: <notification message>" plus the existing digest.
- Placeholder: the Stop event carries `last_assistant_message`. Show it in the inbox at once and replace it when the digest arrives. The inbox keeps working when Sonnet fails.
- The consumer runs only while Brain Fry runs, in a background thread. On start it digests the backlog. No daemon.
- The prompt goes on stdin (no limit on argument length). Each turn sends the prompt (cut to 4,000 characters), the tools used (from the transcript, best effort: name plus file path or the first line of the command) and the reply (cut to 8,000 characters).
- The call runs without the task-file lock. Afterwards the task is reloaded and only the threads that were sent are updated, because events may have changed the task in the meantime. A thread that the model skipped becomes FYI, so that it never loops. A failed call leaves the thread pending.
- Measured on 2026-11-09: about 3.4 s per call. Tested on a real session: kind `answer`, the question copied word for word, a 3-line digest.
- `bf digest` and `bf list` run the reader and the digest by hand, for testing without the app.

### Early summary of a new task (discussed 2026-11-10, parked by Renaud)

- Problem: a new card stays empty during its whole first turn, which can last 10 min or more, because the digest runs only on Stop. Until then the card shows the first line of the first prompt and no digest. Seen on 2026-11-10 (task `26e6084d`): the prompt was `[Image #1]` plus "Don't build it but let's spec it out.", so the card showed only `[Image #1]`.
- What is known, and when:
  - 0 s: the prompt text (hook). Useless when the topic is in a screenshot.
  - 0 s: the pasted image. The transcript's user message holds it as a base64 `image` block (53 KB here, same timestamp as the prompt), followed by a text entry `[Image: source: /private/tmp/...]` that gives a file path.
  - A few seconds, before the first reply: Claude Code writes `{"type":"ai-title","aiTitle":"..."}` into the transcript (internal format; the entry is appended again at each turn, with the same value). It costs us nothing. It sees only the text: "Organized mode tab summaries" for a text prompt (good), "Image-based feature spec" for the screenshot prompt (useless). Some transcripts also hold `custom-title` and `agent-name` entries.
  - 10 s and later: tool calls with their descriptions. In `26e6084d` the agent wrote no visible text for minutes, and the descriptions gave only weak hints.
- Proposal (not decided):
  1. No model call: until the first digest, the card shows the prompt in gray in place of the digest, and the fallback title skips `[Image #N]` lines.
  2. An early digest: the first UserPromptSubmit of a task without a title queues one Sonnet call on the prompt plus its images (from the transcript). It returns title, short title and a digest of the goal, in about 4 s. Stop still rewrites the digest. One call per new task, not per turn. A fork gets its call at its own first prompt.
  3. Do not use `ai-title`: it fails on screenshots, and it is one more internal format.
- Open for Renaud: whether the early title is final (the "set once" rule; recommended, since the prompt plus the image name what was asked) or replaced once by the Stop digest; whether one more Sonnet call per new task is acceptable.
- Not tested: images in `claude -p`, probably through `--input-format stream-json`. Fallback: give the image's file path and let the call read it (a few seconds and one tool turn more).

## App

Brain Fry is one Mac window. Chosen on 2026-11-09 instead of the TUI, see Rejected.

- One Python process. pywebview opens a native window that uses the system WebKit (WKWebView), so no browser is bundled. The front end is plain JS: xterm.js for 4a and 3b, CodeMirror 6 for 3a.
- A local websocket in the same process carries the terminal bytes between xterm.js and the PTYs, and pushes board and inbox updates to the front end. Jupyter's terminal works the same way (terminado + xterm.js).
- The app owns the PTYs. Each live session is a `claude` child process in a PTY, with `TERM=xterm-256color` and `COLORTERM=truecolor`. Each terminal tab (3b) is a shell in a PTY.
- Children get a cleaned environment. When Brain Fry is started from inside Claude Code or VS Code, it inherits about 30 variables that they set for their own children (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_ENTRYPOINT`, `VSCODE_*`, `TERM_PROGRAM`, ...). A `claude` that sees them may believe that it is nested or attached to an IDE. The app removes a precise list of them (`CHILD_ENV_DROP` in `util.py`) and every `VSCODE_*` variable, not every `CLAUDE*` variable, because a user may set `CLAUDE_CODE_*` variables on purpose.
- The front end keeps one xterm.js instance per live session and shows the selected one in 4a. Each instance keeps its own scrollback. The backend keeps the last few MB of each PTY's output, so a reloaded front end can replay it.
- Quitting the app ends all live sessions: a turn in progress is killed, its task goes to the inbox (Hooks, "Turn cut off"), and `--resume` brings the conversation back. Quitting asks for confirmation while a task is working. Planned: closing the window keeps the app running. Built in step 3: closing the window quits (with the same confirmation).
- Spawning a PTY child: the app has threads (Cocoa, asyncio, digest worker), so `pty.fork()` (Python code between fork and exec) is unsafe. `subprocess.Popen` forks and execs in C; a 3-line Python wrapper then takes the PTY as its controlling terminal (TIOCSCTTY, so that Ctrl-C and SIGWINCH reach the child) and execs `claude`. Tested: size, SIGWINCH, Ctrl-C.
- Code: `app/core.py` (state, commands, PTYs, the reader every 0.5 s, the digest worker thread, a sweep every 60 s), `app/server.py` (one port: static files, `/file/<task id>/<path>` for the images and PDFs of 3a, `/ctl` websocket for state and commands, `/pty/<task id>` websocket for terminal bytes), `app/main.py` (window, single instance through a lock on `~/.brain_fry/bf.lock`), `web/` (plain JS; the libraries are vendored in `web/vendor/`, see 2a, 3a, 3b).
- The server listens on 127.0.0.1 only, but a web page that I open in a browser can still reach it: a browser opens a websocket to any address (no same-origin rule for websockets), and DNS rebinding lets a site point its own name at 127.0.0.1. Without a check, such a page could find the port, send `shell.new` and type a command into the shell. So every request must carry `Host: 127.0.0.1:<port>` or `localhost:<port>` (a rebinding page sends its own name), and a request with an `Origin` header must come from the app's own page. Clients that are not browsers (tests, scripts) send no `Origin` and pass; they run as me anyway. Built 2026-11-10, tested in `test_app_backend.py`.
- The backend pushes the whole state (all tasks) after every change, coalesced over 50 ms. Simple, and cheap for dozens of tasks.
- Resume: `claude --resume <id>`. A task that was never prompted has no transcript to resume, so it gets `claude --session-id <id>` again; a fork that was never prompted is forked again.
- `~/.brain_fry/owned.json` lists the tasks whose `claude` runs in the app. After a crash, the app marks them not live at the next start (those processes died with it).

## Browser (3a)

Asked by Renaud on 2026-11-10: a decent browser in panel 3 that keeps its cookies and has uBlock. Built 2026-11-10. The research behind the choice of engine is under Rejected.

- Engine: the system WebKit, as a second native view. A browser tab is a tab of 3a (`kind: 'web'`, `web/browser.js`) whose element is a placeholder; the page is a WKWebView (`app/browser.py`) added to the window over the placeholder's rectangle. The page sends the rectangle at every frame and every 250 ms (`browser.place`; WebKit pauses frames while the window is covered). The view hides when its tab is not on screen (another tab or task, Organize mode).
- Why not an `<iframe>`: most sites forbid framing (`X-Frame-Options`, CSP `frame-ancestors`), and WebKit blocks the cookies of an iframe from another origin as third-party, so logins fail.
- A native view always paints above Brain Fry's page. While an HTML dialog covers 3a (the project picker, the splash), the view is hidden and a snapshot of it (`browser.snapshot`, JPEG) fills the placeholder. A toast that would fall on the page moves over 4a. (For PDFs, a native view was rejected for this reason; a browser has no other way.)
- Cookies: one persistent website data store (`WKWebsiteDataStore(forIdentifier:)`, macOS 14+) for every tab of every task, so a new tab has them. Its id is a uuid5 of the Brain Fry home, so tests (`BRAIN_FRY_HOME`) have their own profile. WebKit keeps it in `~/Library/WebKit/python3/WebsiteDataStore/<id>/`, a folder named after the process: if Brain Fry becomes a `.app`, the profile must be moved. pywebview's private mode wipes the default store at each start, not this one (tested).
- Session cookies (no expiry) die with the process in WebKit, as in any browser without session restore (tested). Brain Fry saves them every 30 s and at quit to `~/.brain_fry/browser/session_cookies.json` (mode 600, its folder 700: it holds logins) and sets them back at start. Tested in the window: the first request after a restart carried both kinds of cookie.
- My Firefox cookies (`firefox.py`, asked by Renaud on 2026-11-10): copied once, at the first start of the browser (when `browser/firefox_import.json` does not exist yet), and again by "Overwrite my cookies" in the burger menu. Per site, Firefox's cookies replace the browser's: the cookies of every site that Firefox has cookies for are deleted first (WebKit's data records, one per registrable domain: `google.com`), so that two logins never mix. The sites that only Brain Fry knows keep theirs. Page loads wait during the copy (20 s at most). Open pages keep what they loaded: a reload uses the new cookies.
- What is copied: the persistent cookies of the default container of the profile that Firefox opens (the `Install` section of `profiles.ini`, else the profile whose cookies changed last). Firefox locks `cookies.sqlite` while it runs, so Brain Fry reads a copy of it and of its WAL (the latest writes, about 850 KB here), in a private temp folder deleted at once. Skipped: Firefox's session cookies (it keeps them in memory and in its compressed session store, not in `cookies.sqlite`), partitioned cookies (`^partitionKey=`), container cookies (`^userContextId=`), expired ones. Firefox 13x stores `expiry` in milliseconds (seconds before) and `sameSite` 256 for "not set". CFNetwork caps a cookie's lifetime at 400 days. Renaud's profile on 2026-11-10: 2,714 rows, 2,530 in the default container, 748 hosts.
- The burger menu (☰, next to the logo, `web/menu.js`) holds actions that I need rarely. Two: "Overwrite my cookies", with the time and counts of the last copy. No confirmation: a click that I did not mean replaces the cookies of a site with Firefox's, where I am logged in anyway.
- "Show shortcuts" (asked by Renaud on 2026-11-11: "whatever is easy"): a modal (`#keys` in `index.html`) that lists every key of the app, in three columns, one group per context (everywhere, Dev mode, files and PDFs, browser tab, explorer, Organize mode, Review mode, pickers, new card dialog). The list is static HTML written by hand, read from the key handlers of the front end on 2026-11-11: a new or changed key must be added there too. Esc or a click outside the box closes it; while it shows, a keydown listener on `window` (capture phase, so before every listener of `document`) swallows every key, so that nothing reaches a terminal or a mode. It hides the pages of 3a (`covered()` in `browser.js`), and shares `.modal` with the pickers and the commit dialog of Review mode. `.modal` had no z-index, so `#tree-collapse` (2) and `#sel-chip` (20) painted over every modal and could be clicked through its backdrop (seen in a snapshot, then checked with `elementFromPoint` for Cmd+P). Since 2026-11-11 (Renaud: "fix it"): `.modal` 40, `#toast` 45 (a toast must stay above a dialog, for example a failed create in the new card dialog, as before by page order), the menus 50 and 60 unchanged. Tested with a sandbox selftest: with Cmd+P and with "Show shortcuts" open, the modal is on top of both elements, and the toast on top of the modal; the commit dialog not tested (same class). No key opens it (not asked). Tested with a sandbox selftest (window visible): opens from the menu, Cmd+B swallowed, Esc and a click outside close it, a click inside does not, Esc in Organize mode closes only the modal; a WebKit snapshot checked the look. Renaud has not tried it yet; the app must be restarted.
- uBlock Origin Lite, the Safari build of the official release (`ublock.py`). `bf ublock` downloads it, refuses it unless its SHA-256 matches the one that GitHub publishes for the asset (`digest` in the releases API), and unpacks it into `~/.brain_fry/extensions/ublock-lite/`. `bf install` runs it too; `bf ublock --zip` installs a local file. It is loaded through WebKit's extension API (`WKWebExtension`, macOS 15.4+), with all its permissions granted. Full uBlock Origin cannot run: it needs `webRequestBlocking`, which WebKit does not have (and Chrome removed in 2025); only Firefox keeps it.
- The extension needs a fixed identity (`uniqueIdentifier`, base URL `webkit-extension://ublock-lite/`), else WebKit gives it a new one at each start and its settings are lost (tested). Its own pages (popup, dashboard) work only in a view made from `context.webViewConfiguration()`.

Page loads wait until 2.5 s after the load, so that a restored tab shown at once is filtered (tested). The first start after an update compiles the rules again (about 5 s in the spike): those seconds leak.

Its generic cosmetic filters (ad slots hidden on any site) run only in its "complete" mode, by design. Both tested offline in a spike (deleted on 2026-11-10). WebKit applies uBOL's CSS only in a page on screen: uBOL inserts it in a `requestAnimationFrame`.
- uBlock's popup: the uBlock button of the toolbar shows uBOL's popup page in an NSPopover. WebKit loads the page but did not call the delegate `presentActionPopup` (macOS 26.7), so Brain Fry shows `action.popupWebView()` itself.
- Toolbar (the bar of 3a): back, forward, reload / stop, address (a URL, a host, `localhost:5173`, or words: a Google search), find (Cmd+F; Enter, Shift+Enter, Esc), uBlock. A tab is named after its page's title; its tooltip is the URL. Cmd+N B (then a pane's digit, see the grid) opens a tab with the address field focused; until 2026-11-10 it was "+ Browser" or Cmd+T.
- Keys: a key monitor (`NSEvent` local monitor) sees each key before WebKit. While a page has the focus, Brain Fry's Cmd keys (Cmd+Up/Down, D, E, Shift+D, N, J, T, P, B, G, 1-9) and the browser's keys that live in Brain Fry's page (Cmd+L, W, F) go to the page, with the key of the page that had the focus (`browser` message `key`, dispatched as a keydown). Cmd+W, forwarded, closes the tab on screen in the pane that I use, like any Cmd+W ("2a, 3a, 3b").
- Focus: a tab that I open or click gets the keyboard at its next placement (`browser.place` with `focus`). A view that hides gives the keyboard back to Brain Fry's page.
- `window.open`, `target=_blank` and Cmd+click on a link open a tab of the same task (Cmd+click: in the background). A popup's view is made with the configuration that WebKit passes, so `window.opener` works (OAuth logins). `window.close()` closes the tab. Links with another scheme (`mailto:`, `zoommtg:`) go to their app.
- Closing a tab ends its page. Found by Renaud on 2026-11-10: a closed YouTube tab kept its sound. Removing the view from the window is not enough while something holds it, and the tab held itself: page --> its WebKit extension tab --> page, a cycle through an Objective-C object that PyObjC cannot collect. The close now pauses the media, closes fullscreen and picture in picture, cuts the cycle, and closes the page (`_close`, WebKit SPI). Tested in `host_check.py`: with a view still held, the old steps left a looping sound playing, the new close stops it. A hidden tab (another tab or task) plays on, as a background tab in any browser.
- Downloads (`Content-Disposition: attachment`, a type that WebKit cannot show, `<a download>`) go to `~/Downloads` under a free name (`a (1).pdf`), with a toast "Show in Finder". JS alert, confirm, prompt and file pickers are native panels. Right click --> Inspect Element, and Safari's Web Inspector, work in the pages.

## Reply trailer and resume note (not built), auto-advance

Three additions from a review on 2026-11-09. It compared the design with my Claude Code transcripts (296 sessions, 1,217 prompts, 2026-08-27 to 11-09) and with research on interruptions and on supervising automation. The analysis and its sources are in RESEARCH.md.

Status on 2026-11-10: auto-advance is built. The reply trailer and the resume note are specified but not built: no code parses `[needs: ...]`, the hook has no SessionStart handler, `bf install` writes no `trailer_prompt.md`, and nothing asks for a resume note. The text below describes how they will work.

**Reply trailer (not built): the agent says what it needs from me**

- Every reply of an agent ends with one line: `[needs: KIND] TEXT`. KIND is a thread kind:
  - `answer`: the agent asked me a question. TEXT is the question.
  - `rule`: I must choose between options or rule on a trade-off. TEXT names the choice and its options.
  - `review`: the agent changed something that I should check. TEXT says what to check and where.
  - `fyi`: nothing is needed from me. TEXT is the outcome in a few words.

  When several apply, the first in this order wins. `blocked` still comes from the Notification hook.
- Why: the agent has the whole context of its turn, while Sonnet infers the kind from a reply cut to 8,000 characters. The line also shows in 4a, at the end of the reply. In the transcripts, only 13% of final replies had a question in their last paragraph, so most trailers will say `review` or `fyi`.
- The instruction is `~/.brain_fry/trailer_prompt.md`, written by `bf install`. The hook prints it on SessionStart, and Claude Code adds the stdout of a SessionStart hook to the model's context (documented; it does not show as a message in the terminal). SessionStart fires on startup, resume, clear, compact and fork, so the instruction comes back after a compaction. This reaches every session in a Brain Fry project, wherever it was started (Brain Fry, VS Code, a plain terminal), and changes no CLAUDE.md. On SessionStart the hook writes no event file.
- Not `--append-system-prompt`: it reaches only the sessions that Brain Fry starts. And Claude Code records the system prompt at a conversation's first request and resends that record until a compaction (`--system-prompt-snapshot`, on by default), so an edit of the text would not reach the existing sessions.
- The hook prints nothing for scripted `-p` runs, because a script may parse their output: it skips when `CLAUDE_CODE_ENTRYPOINT` is `sdk-cli`.
- At Stop, Brain Fry reads the last non-empty line of `last_assistant_message`. It accepts `[needs: KIND] TEXT` in any case, also inside `*` or backticks. No such line, or an unknown KIND: no trailer, and the kind comes from Sonnet as before.
- With a trailer, the thread gets its kind and question at once, and the inbox row shows the trailer instead of the start of the reply. Sonnet still writes the title and the digest; its prompt says that the trailer is the agent's own claim. When Sonnet's kind differs, the thread keeps it as `**Sonnet kind**` and the inbox row shows a small mark. These disagreements show how far each label can be trusted. That matters: research on diagnostic aids finds that a label that is right less than about 70% of the time does worse than no label (Wickens & Dixon 2007).
- The reply in the task file stays verbatim, trailer included.
- First text of `trailer_prompt.md`:

```
End every reply with one last line, and nothing after it:
[needs: KIND] TEXT
KIND is one of:
- answer: you asked me a question. TEXT is the question, in one sentence.
- rule: I must choose between options or rule on a trade-off. TEXT names the choice and its options.
- review: you changed something that I should check. TEXT says what to check and where.
- fyi: you need nothing from me. TEXT is the outcome in a few words.
If several apply, use the first in this list. If you have several questions, TEXT holds the most important one and the others go in the reply above.
```

**Resume note (not built): one line from me when I leave a task unfinished**

- When I move a task into a hidden column (later, more later, never), a one-line input opens and takes the focus: on the task's row in 1a (Dev mode), or on its card (Organize mode). Enter saves. Esc closes it without saving. Up/Down, Cmd+Up/Down, a click on another task or a mode switch close it and save what I typed.
- While the input is open, letters and Left/Right go to it, not to the Organize keys.
- No input on archive (the task is done), on answer (the agent continues and will reply), or on a move between working and planning (the task stays in view).
- I write the note; nothing is prefilled. Why: Leroy & Glomb 2018 found that a short plan, written when leaving an unfinished task (where I stopped, what is left), reduced the attention that stays on it and improved the next task. The move alone records no plan, and the digest is Sonnet's summary of the past, not my plan.
- The note is saved as `resume_note` in the frontmatter. It shows on the card, and under the digest in the inbox row when the task comes back. My next prompt to the task (UserPromptSubmit) removes it. Each note is also logged in `events.jsonl`, so that I can see later how often I write one and whether the habit lasts.

## Worktrees (discussed 2026-11-10, not built)

Renaud asked whether a task should get a git worktree by default. Decision: write it down, do not build it now.

- Today no task gets a worktree. A new task runs `claude --session-id` in the project root (`actions.new_task`), a fork in its parent's `cwd` (`actions.fork_task`), a resume in the task's `cwd`. That `cwd` is set when the task is born and never updated from later events (`events.py`). The only support is passive: the hook walks up from `cwd`, so a session that Renaud starts with `claude -w` (Claude Code 2.1.322 creates `.claude/worktrees/<name>/`) still lands in its project. `.claude` is in `~/.gitignore_global`, so worktrees there are ignored by git; `.brain_fry/` is too, so a worktree holds no `.brain_fry/` and the walk-up reaches the project's.
- For: isolation (an agent does not see another agent's half-finished edits, its tests do not fail on them); a diff per task (in a worktree, "Diff vs HEAD" shows only this task's work, which v2's review needs); closing a task = merging its branch and removing its worktree, the "close it" step of brain_fry.md.
- Against a default for every task:
  - A worktree starts from HEAD, not from the working tree. On 2026-11-10 this repo had 1 commit, 28 modified files and 17 untracked ones: a worktree task would not have seen the day's work. A default would force a commit before each task, against Renaud's way of prototyping.
  - Gitignored files are missing in a worktree: `.venv` (uv rebuilds it), `.env`, data folders, checkpoints. In an ML project the agent may not find its data.
  - Many tasks write no code (quick questions, research). At 7.6 new sessions per active day, worktrees and branches pile up, and each task that writes adds a merge. Conflicts move from silent and continuous (one shared folder) to explicit at merge time: one more decision in the inbox.
  - Some projects may not be git repos.
  - SWITCHdrive syncs `.claude/` (its exclude list has only `.venv`, `node_modules`, `target`, `*_nosync`), so each worktree is uploaded (about 9 MB of tracked files for this repo). A `*_nosync` folder avoids it, but uncommitted work in it would have no backup. Minor for code repos.
- Renaud's `land` instruction (`~/.claude/CLAUDE.md`) already describes an opt-in habit: a worktree when another agent works in the main tree.
- Evidence still missing: the 67% of RESEARCH.md (two concurrent agents shared a project folder) measures how often the risk was present, not how often harm happened. Default worktrees cost something on every task, so they pay off only if collisions are frequent. Proposed count, from Claude Code's transcripts: Edit and Write tool calls carry a file path and a timestamp; count the cases where two sessions of one project edited the same file within about 30 minutes, and the turns where a test run failed while another session was editing. A proxy: it misses conflicts that span files and counts harmless overlaps, but it is much closer to harm than sharing a folder. Around 1 turn in 200: worktrees would solve a rare problem at a daily cost. Around 1 in 10: a default is justified.
- Two questions for Renaud decide it: how often do two agents that write code run in one repo at once, and is he willing to commit before starting such a task?
- If built:
  - Opt-in: a modifier in the Cmd+T picker (e.g. Option+Enter) for "new task in a worktree", and `"worktree": true` per project in `projects.json` for a project default.
  - Brain Fry creates the worktree itself (`git worktree add .claude/worktrees/<id> -b bf/<id>`) and starts `claude --session-id` there, rather than passing `-w`: as with `--session-id`, it knows the path from the start, and `--resume` must run there.
  - 2a and "Diff vs HEAD" follow the task's `cwd`, not the project root.
  - Archive: a clean worktree whose branch is merged is removed with its branch; otherwise Brain Fry asks (merge, keep, discard). Renaud's `land` steps become a Brain Fry action.
  - Open: what a fork of a worktree task gets (the parent's worktree, or a new one from the parent's branch, which needs a commit).
  - Middle path: every task starts in the main tree and moves into a worktree once it starts writing (Claude Code's EnterWorktree tool does that during a session). Brain Fry would then have to update the task's `cwd` from the hook events.

- No sections for stashes, remotes, tags or submodules (Renaud: "I don't need to stash anything").

2a, the log:

- Commits of all local branches, of the remote-tracking branches, and the detached HEADs of the worktrees (`git log --branches --remotes <heads> --date-order`), newest first. A toggle "Current branch" keeps only the history of the current worktree's HEAD (SourceTree's "All branches" / "Current branch"). Stashes are never shown.
- Labels before the description: local branches, remote branches, tags, and "wt: <name>" on the HEAD of each worktree. The hash has 7 characters, the author is the name only, the date is local ("10 Nov 14:03", with the year when it is not the current one).
- The graph: the backend computes the lanes (a list of open lines of descent, which each commit continues or opens), and the front end draws them in an SVG per row, one color per lane. No library.
- 1,000 commits are loaded at first, then 1,000 more when the list comes near its end. Each load asks again from the first commit (up to 20,000) and the backend computes the lanes again, so it keeps no state between pages. The graph is one small SVG per row.
- A selected commit: 2b shows its message and its changed files (`git diff-tree -r -M --name-status`, against the first parent; a root commit against the empty tree), 3b the diff of a file, with no buttons.
- When the refs change (see Refresh), the log reloads and the selected commit stays selected, by hash.

2b, the files:

- "Uncommitted changes" selected: two lists, Staged files over Unstaged files (SourceTree's order), each flat and sorted by path (the file name, then its folder in gray). Each row has a status letter: M, A, D, R (old --> new), T, `?` (untracked), U (conflict). A file that is partly staged appears in both lists.
- A button on each row (as VS Code's + and -) stages or unstages the whole file, and Space does it for the selected row. Each list's header has Stage all / Unstage all.
- During a merge, a rebase or a cherry-pick, a banner says so, and the conflicted files come first, in their own group. Staging one marks it resolved, as `git add` does. The resolution itself happens in the editor of Dev mode or through the agent.
- Untracked files are listed one by one (`-uall`), up to 1,000; beyond that, by folder.
- Right-click on a file: Open (switches to Dev mode, file tab in 3a), Discard changes (unstaged files only, see 3b), Copy path, Copy relative path.
- Commit (Renaud, 2026-11-10: no message area on screen, a button that opens the message): a Commit button in the header of the staged list, enabled while at least one file is staged; Cmd+Enter anywhere in the mode does the same. It opens a dialog: the branch and the worktree, the staged files, a field for the message, Cancel and Commit. Cmd+Enter in the field commits; Esc closes the dialog and keeps the draft. The backend runs `git commit -F -` with the message on stdin and `GIT_EDITOR=true`, so that no editor opens. The repository's hooks run; when the commit fails, the dialog stays open and shows their output. A commit that takes more than 60 s is stopped (for example, a signing key that waits for a passphrase). The draft is kept per worktree until the commit, in memory only. No amend (Renaud).

3b, the diff:

- Unified, 3 lines of context, two columns of line numbers, removed lines in red and added lines in green, no syntax highlighting (as SourceTree). An unstaged file shows index --> work tree (`git diff`), a staged file HEAD --> index (`git diff --cached`), a file of a commit its first parent --> the commit.
- Each hunk header has its buttons: "Discard hunk" and "Stage hunk" in an unstaged file, "Unstage hunk" in a staged file. N and P move to the next and previous hunk; Space stages or unstages the hunk at the cursor.
- Single lines (Renaud, 2026-11-10): a click on a + or - line selects it, Shift+click extends the selection, Cmd+click adds a line, Esc clears it. While a hunk has selected lines, its buttons become "Stage n lines" (or "Unstage n lines") and "Discard n lines", and Space acts on the lines. The patch keeps the hunk's context and only the selected changes, as git gui does: to stage, an unselected - line becomes context and an unselected + line is dropped; to unstage (`--reverse`), an unselected + line becomes context and an unselected - line is dropped. `git apply --recount` recounts the lines, so the counts of the @@ line do not matter. The front end sends the indexes of the lines with the hash of the hunk, so the check below applies to lines too.
- Discard (Renaud, 2026-11-10): a hunk, selected lines, or a whole file, in unstaged files only (index --> work tree); a staged change must be unstaged first. Cmd+Backspace (Brain Fry's key for Delete in 2a) or the button, then a confirmation, as in SourceTree and VS Code. The backend applies the patch to the work tree with `git apply --reverse`, after it saved that patch in `<project>/.brain_fry/discarded/<time>-<file>.patch`; the toast offers Undo, which applies it again. An untracked file goes to the Trash of macOS, as Delete in 2a does. Discard rewrites a file under a running agent, which checkout also does; it is allowed because it touches only what Renaud chose, after a confirmation, and can be undone.
- A hunk is staged as git gui does it: a patch made of the file's header and that one hunk, given to `git apply --cached` (`--reverse` to unstage). The front end sends the path and a hash of the lines of the hunk that it shows. The backend runs the diff again, looks for a hunk with the same lines (its position may have moved), and applies its own bytes. The patch is never rebuilt from the page's text: line endings (CRLF), encodings and trailing spaces must stay exact to the byte.
- If no hunk has the same lines (the agent rewrote that part of the file, or ran `git add`), nothing is applied, whether to stage, unstage or discard: a toast says that the file changed, and the diff reloads. A change elsewhere in the file does not block the hunk on screen. A discard therefore never removes lines that Renaud has not seen.
- After a stage or an unstage, the lists and the diff reload. The selection stays on the file, or moves to the next file of the same list when the file left it. The current hunk keeps its number, so it is now the next hunk.
- Whole file only, no hunks: untracked files (shown in full as added, text up to 2 MB as in 3a), files that are new in the index or deleted (a hunk of them cannot be applied alone), binary files ("Binary file."; their sizes are not shown), renames and copies, changes of mode only, submodules (the old and new commit). For these the bar of 3b has the buttons Stage file, Unstage file, Discard file (Move to Trash for an untracked file) or Mark resolved.
- The selected lines stay inside one hunk: a click in another hunk starts a new selection. They are cleared when their hunk changes.
- A diff of more than 5,000 lines shows the first 5,000 and a "Show all" button.

Refresh:

- While Review mode is on screen: the status of the current worktree every 2 s, at once when a state push shows that a task of the project changed (a hook event), and after each action of the mode. The diff of the selected file is asked again at each refresh and drawn again only when its signature changes, at the same scroll position. The counts of the other worktrees (panel 1) every 10 s. Nothing runs while the mode is hidden.
- Every git call of a poll uses `--no-optional-locks`. Without it, `git status` refreshes the index and holds `index.lock` for that moment, and an agent's `git add` or `git commit` at that moment fails with "index.lock exists". Git added the option for tools that poll in the background.
- The log reloads only when the refs or the worktrees' HEADs change (`git for-each-ref`, checked at the same poll).
- A stage, an unstage or a commit that meets `index.lock` (an agent runs git) retries for 1 s, then says so in a toast.

Backend and front end:

- `git.py`: every call goes through the git CLI (`git -C <worktree>`, `-z` outputs, `-c core.quotepath=off`, `GIT_TERMINAL_PROMPT=0`, no pager), with the cleaned environment of the children (`CHILD_ENV_DROP`) and a timeout. No pygit2 or GitPython: one more dependency, and the CLI behaves exactly as the one that agents and Renaud run (worktrees, hooks, config, the lock).
- Commands on `/ctl`, with a request number: `git.state` (worktrees, branches, the status of the current worktree), `git.log` (a page), `git.commit_info`, `git.diff`, `git.stage`, `git.unstage` and `git.discard` (a file, a hunk or lines), `git.undo_discard`, `git.commit`. Git data is not part of the pushed state: the front end asks for it while the mode is on screen. `git.state` also lists, under each worktree, the tasks of the project whose folder is in it (core.py passes them).
- `web/review.js` and `web/review.css`: the four panels, the commit dialog (`#rv-dialog`), the graph, the keys of the mode. In app.js, `setMode`, `render` and the key handler call into review.js; #dev holds the panels (`#review`) beside 4a, and the classes `review` and `rv-agent` on #dev hide 1, 2a, the middle column and 4a. Keys are single letters while a panel of the mode has the focus, as in Organize mode; not while 4a or the commit dialog has it. Splitters and remembered sizes as in Dev mode.
