# Design

## Layout

numbered from the left to right (1,2,3, ...) and top to bottom (a,b,c, ...)

### Organize mode

a kanban-style *board*. each T is assigned to a project. the columns are the prio of a T; the status of a T is a small color on its card (see Concepts)

1: working
2: next
3: planning
4: later (by default, these Ts are hidden. shortcut to toggle them, together with "more later", "never" and archived Ts)
5: more later (ditto)
6: never (ditto)

archived Ts stay in their prio column, gray, and are hidden like "later"

### Dev mode

a vs-code-style view, but with an inbox and NO agent tabs

1a: inbox (NOT agents running);  the inbox is a filter over tasks that have an unread reply; either T is finished (so I need to review or answer) or blocked (permission). blocked Ts sort first. T summary text is generated by Sonnet. prompt is in ~/.brain_fry/inbox_prompt.md. selecting a T marks it read and shows its CC session in 4a; it leaves the inbox when answered or archived. actions: answer (in 4a), archive the T, or split it in 2 Ts (fork).
1b: task threads (TT); opens the thread as a tab in 3a, jumping to it in 4a's scrollback comes later. hidden when the inbox is empty

2a: file explorer (root = the selected T's project)

3: a 2x2 grid of panes, numbered 1 (top left, the main pane), 2 (top right), 3 (bottom left), 4 (bottom right). each pane has its own tabs: files, browser, terminals (xterm.js). a pane shows only while it has tabs. no terminal by default.
- Cmd+N, then T (terminal), B (browser) or F (new untitled file; the first save asks where), then 1-4: created in that pane. no digit (wait 1 s): pane 1. no hint on screen. nothing is created and then moved.
- Cmd+J, then 1-4: focus that pane (J: jump; F stays for find).
- drag a tab to another pane; to the right of a single column: two columns (same for the bottom)
- Cmd+T: new task

open files and terminal tabs belong to the selected T and are restored with it

4a: agent conversation: the selected task's Claude Code CLI in a terminal view (xterm.js).

## Concepts

- brain_fry (BF): the app (a Mac window).
- task (T): corresponds to a CC session, with some of my metadata (prio, status, summaries). lives in <project>/.brain_fry/<session-id>.md
- task thread (TT): correspond to a single question-answer (a conversation thread) with CC. belongs to a single task
- prio: the column of a T on the board: working, next, planning, later, more later, never. changes only by my keystroke
- status: set automatically by CC hooks: working (orange), blocked (red), waiting for me (green), done / archived (gray). live: a separate dot, not a status
- fork (split): a new T that starts from a copy of an existing T's conversation (`claude --resume <id> --fork-session`)
- layout: everything that is open in the four panes of column 3: all their tabs (files, terminals, browser pages, threads, whatever comes in a pane) and where each one sits. never files only
- board: a single board for BF
- project: a folder on my local computer, in which i'm working on. basically, projects are based on the pwd of a given project. projects are added / edited in projects.json in ~/.brain_fry/projects.json; this file also contains "views", sets of projects (e.g. perso, teaching, electricity_markets)



## Tech stack

- Python, UV. No sqlite: tasks are markdown files in <project>/.brain_fry/
- Sonnet via `claude -p`
- CC hook: bash + jq, writes one file per event to <project>/.brain_fry/events/
- GUI: pywebview (system WebKit), xterm.js (terminals), CodeMirror 6 (files)

## Core

The spec above is Renaud's: change it only when he asks. Everything below is written by Claude.

- DESIGN.md (this file) holds the spec and the core: what every agent needs, whatever it works on. Agents load it at each start, so it stays short.
- DESIGN_DETAILS.md holds one section per area: decisions, rationale, facts about Claude Code, tests, open items ("Still open"), rejected options ("Rejected"). Read the section of the area that you work on before you change it. New decisions go there. Change the core only when a decision changes something stated here.

### Files

- Global, in `~/.brain_fry/` (`BRAIN_FRY_HOME` moves it): `projects.json` (projects; its views are ignored in v1), `inbox_prompt.md` (the digest's prompt), `hook.sh` (a copy of `src/brain_fry/hook.sh`), `owned.json`, `selection.json`, `logs/bf.log` and `logs/hook.log`, `extensions/ublock-lite/`, `browser/` (cookies, mode 700).
- Per project, in `<project>/.brain_fry/` (ignored by `~/.gitignore_global`): one task file per session, `<session-id>.md`; `project.json`, the project tabs (below); `events/`, the spool that the hook writes (one file per event, deleted once applied); `events.jsonl`, the log of applied events; `consume.lock`; `discarded/`, the patches that Review mode's Discard removed (for Undo).
- `bf init` (or File > Add New Project... in the window) creates `.brain_fry/` and registers the project. `bf install`, once per machine and safe to run twice, adds the hook to `~/.claude/settings.json`, copies it, writes `inbox_prompt.md` and installs uBlock Origin Lite. A banner asks for `bf install` when the installed hook differs from the packaged one, so any change to `hook.sh` needs it.

### Task file

- The task file is the record. Claude Code's transcripts are internal and deleted after 30 days, so a task holds everything that Brain Fry needs.
- Layout: YAML frontmatter, `# Notes` (only a task created in Organize mode has notes), `# Digest`, then `# Threads`, with one `## n | timestamp | kind` section per turn (digest, question, prompt, reply). All free text is written as `> ` lines, and the parser reads only the other lines as structure.
- Frontmatter: `session_ids`, `cwd`, `transcript_path`, `project`, `parent`; `title`, `short_title`; `prio` (changed only by Renaud's keys); `status` (changed only by events); the flags `live`, `inbox`, `unread`, `pinned`, `held`; `created`, `updated`, `opened`; the workspace, `open_files`, `terminal_tabs`, `browser_tabs`, `finder_tabs`.
- Thread kinds: `working` (prompt sent), `pending` (reply arrived, not digested), `interrupted`, `imported`, then the digest's kind: review, answer, rule, FYI, wait, blocked.

### Hooks

- One bash + jq script, registered in `~/.claude/settings.json` for UserPromptSubmit, Stop, Notification and SessionEnd, so it runs in every project. It walks up from the payload's `cwd` to the nearest folder that has `.brain_fry/` (it stops below `$HOME`) and writes the payload, plus `bf_ts`, as one file in that spool (temp file, then rename). It always exits 0, and exits at once when `BRAIN_FRY_INTERNAL` is set (Brain Fry's own `claude -p` calls). Its only output is Renaud's editor selection on UserPromptSubmit (DESIGN_DETAILS.md, "Selection as context").
- The app applies the spools every 0.5 s (`events.py`, under `consume.lock`). Event --> task:
  - UserPromptSubmit: a new thread, status working, `inbox` and `unread` off.
  - Stop: the reply (`last_assistant_message`), thread `pending`, status waiting, `inbox` and `unread` on. A bare `close` (or `x`) prompt whose reply ends with `closed :-)` archives the task.
  - Stop while background agents or workflows run (its `background_tasks`): the reply, thread `pending`, but status stays working and `inbox` stays off. Their results start the next turn, whose Stop is the real end.
  - Stop while only background shells or monitors run: status working, `inbox` off, `held` until the digest. Kind `wait` (the agent will go on by itself) keeps it so; any other kind, or a failed digest, puts it in the inbox (`actions.settle_hold`).
  - Notification `permission_prompt` or `elicitation_dialog`: status blocked, `inbox` on.
  - SessionEnd, or the app ends the session (quit, crash): `live` off; working or blocked --> waiting with `inbox` and `unread` on, since the turn was cut off (`actions.end_session`).
  - The dialog of a blocked task closes: no hook fires; Claude Code's process files show it (see Claude Code's internal formats).
- A session that started outside Brain Fry becomes a task at its first UserPromptSubmit, Stop or Notification. Its earlier turns are imported from its transcript.

### Status, inbox, board

- `prio` is the board column: working, next, planning, later, more_later, never (the last three are hidden by default). `status` is the color: working (orange), blocked (red), waiting (green), done (gray, archived). `live` is a flag that is not shown: a `claude` process runs for the task.
- The inbox holds the tasks of the working column that have `inbox` set or are `pinned`, never archived ones (next, planning and the hidden columns wait; their flags stay). Order: `inbox` set first, then red, then the most recent. Selecting a task clears `unread`. Answering and archiving clear `inbox`. Archiving also unpins.
- Auto-advance: after Renaud answers the selected task, the front end selects the next inbox item 1 s later (a switch in the header turns this off); after an archive, at once, whatever the switch. With nothing left, no task is selected and 4a shows a calm photo (`web/calm/`). The photo shows only while nothing needs Renaud: in Dev mode with no task selected, a task that comes into the inbox is selected at once. Only 4a changes (the idle screen): the dropdown, 2a and column 3 keep the project and the layout of the task that Renaud left, or at start of the task opened last, which is not selected (`S.idle`, `showIdle` in `app.js`).

### Digest

- Sonnet through `claude -p` (the subscription, not the API), in a worker thread of the app: one call per turn, with structured output (title and short title, both set once; digest; kind and question per thread). Guards: `BRAIN_FRY_INTERNAL=1`, `--settings '{"disableAllHooks": true}'`, cwd `~/.brain_fry/`. The inbox shows the start of the reply until the digest arrives, and keeps working when Sonnet fails.

### App

- One Python process, a pywebview window (system WebKit). `app/server.py` listens on 127.0.0.1: static files, `/file/` (images and PDFs of 3a), `/icon/` (macOS file icons for the Finder tabs), `/ctl` (state and commands, websocket; a connection's commands run one after the other, except the slow ones of the Finder tabs, `server.CONCURRENT`), `/pty/<key>` (terminal bytes). `app/core.py` holds the state, the commands and the background jobs. The front end is plain JS in `web/`, with xterm.js, CodeMirror 6 and PDF.js vendored by `frontend/vendor.sh`: no Node and no network at runtime.
- The backend pushes the whole state after every change (coalesced over 50 ms). Commands that need an answer carry a request number.
- Every request must carry `Host: 127.0.0.1:<port>` or `localhost:<port>`, and an `Origin` header, when present, must be the app's page. Without this check, a web page could drive the shells.
- The app owns its PTYs: each live session is `claude` in a PTY (`--session-id` for a new task, `--resume` for an existing one, `--resume --fork-session --session-id` for a fork), each terminal tab of column 3 a shell. Children start through `subprocess.Popen` and a small wrapper (the app's threads make `pty.fork()` unsafe), with an environment cleaned of the variables of Claude Code and VS Code (`CHILD_ENV_DROP`).
- Cmd keys belong to Brain Fry, since a terminal never sends Cmd. While a terminal has the focus, key events go to xterm.js's hidden textarea. Every key is listed by hand in "Show shortcuts" (`#keys` in `index.html`): a new or changed key goes there too.
- A tab of column 3 belongs to a task or to its project (project tabs, DESIGN_DETAILS.md "2a, 3a, 3b"): every view of the project shows the project's tabs first in each pane, a tab opened with no task selected (idle screen, project view) is one, and a double-click on a tab moves it between the two. A tab's `tid` is its owner (a task id or `project:<path>`); `viewTabs(w)` is what a view shows, `inView(tid)` whether an owner's tabs are on screen.
- The browser of 3a is made of native WKWebViews laid over the page (`app/browser.py`). They paint above any HTML, so an HTML dialog over column 3 must hide them.
- Logs: `bf.log` (the app and the `bf` commands) and `hook.log`. The text of prompts and replies, the commands typed in terminals, and browsing history, are never logged.

### Claude Code's internal formats

Brain Fry reads two formats of Claude Code that are internal. It reads them on a best-effort basis and must keep working without them. `CLAUDE_CONFIG_DIR` moves `~/.claude`.

- Transcripts, `~/.claude/projects/*/<session id>.jsonl`: the turns that a new task imports, the tools of a turn for the digest.
- Process files, `~/.claude/sessions/<pid>.json`: which sessions run and where, and the end of a block (`status` leaves `waiting`). Used only while they list the app's own sessions.
- To learn such a format, scan the `claude` binary, which holds the JS source (DESIGN_DETAILS.md, "Hooks").

### Testing

- `uv run pytest`. The JS has no unit tests: check the window with `bf --selftest SECONDS`. It prints the page text, the terminal text and the JS errors; `--selftest-js` runs code in the page.
- The scripts of `web/` share one global scope: a top-level name declared in two of them is no error, and the script loaded last replaces it for every caller. `tests/test_web_globals.py` fails on such a name.
- Always run a selftest in a sandbox: `BRAIN_FRY_HOME` (its own projects.json, lock and logs; required while the app runs), `BRAIN_FRY_CLAUDE` (a fake `claude`), `CLAUDE_CONFIG_DIR` (fake transcripts). With the real files, it would resume real sessions and apply real spools. A task file copied into the sandbox needs its `project` and `cwd` rewritten, else the backend writes to the real task.
- Send key events to the element that has the focus in real use (xterm.js's textarea in 4a), not to `document`. A double-click is two clicks (`detail` 1, then 2): look the element up again before the second, since the first may rebuild it (a tab bar), and an event on a detached element never reaches `document`. Do not name the test's variables after the page's globals (`S`, `B`, `G`, `F`, `C`): a `const B` hides the browser's state. A run whose `document.visibilityState` is `hidden` (the window was covered) does not count: WebKit pauses frames.
- `tests/window/browser/host_check.py` checks the browser in a real window against a local site (`site.py`).
